# 学習の契約と診断

## 今回の方式から再利用できる点

高速の駆動計算と低速の方策計算を分け、各方策ステップで参照の時刻を一度だけ進める。今回の実験は駆動 400 Hz、方策 50 Hz。これはプロジェクトの選択であり、別機体へ無条件に転用する仕様ではない。

方策には IMU 相当の姿勢・角速度、関節位置と速度、指令、前回の行動、参照運動と駆動状態の因果的な内部状態を与えた。critic に追加した真値は推論インターフェースから外す。実機移行時は IMU だけでなく関節のフィードバック、時刻、通信遅延、指令の意味を合わせる。

参照歩容の周期、支持率、予定足上げ高は学習の足場にできるが、それだけで支持脚が荷重を受けられるとは限らない。左右と前後の脚別に誤差を調べ、悪い脚の結果を平均で隠さない。

停止や指令変更でも、発熱等を近似する駆動状態を勝手に冷たい状態へ戻さない。近似状態を実測温度とは表記しない。ピーク能力は常用能力として扱わず、速度依存性と継続時間を利用者管理の根拠ある入力で設定する。

## 変更の分類

| 変更 | 記録すること |
|---|---|
| 形状・重量・慣性・摩擦 | 有効物理が変わったと明記。CAD が同じでも関節慣性の変更は含む |
| 数値ソルバ・刻み幅 | 元値と新値、実エンジンに反映された値、比較区間 |
| 指令・報酬・行動の上限 | 変更した項だけでなく、元の条件を辿れる実験 ID |
| 重みの転用 | actor / critic / 探索分布のどれを移したか、最適化器・更新回数を再開したか |
| 診断の追加 | 状態・乱数・センサ履歴を変えていないか、呼出し回数が同じか |

同じ seed でも物理を変えれば軌道とその後の学習は変わる。停止までの時間だけで故障率や因果関係を断定しない。

## 接地時の異常を追う

1. エラーになる入力をそのまま保存する。直前までの実出力と、返却に失敗した計算を区別する。
2. 数十回分のリングバッファへ、関節名、位置・速度、目標、実トルク、駆動状態、姿勢、接触、エピソード ID を記録する。
3. ラッパーは本来の計算を一度だけ呼ぶ。センサの遅延評価を発火させる読み方で接触履歴を変えない。使用するバージョンの実装を確認する。
4. 接触力が法線成分だけなら、摩擦を含む全力・全モーメントと呼ばない。単純なトルク積分で説明できない速度変化を直ちにソルバのバグと決めつけない。
5. 関節順・単位・ゼロ点・慣性・接触形状を確認し、原因候補を一つずつ有限試験する。
6. 早期停止の元データを残す。後続処理は実際の正常終了を確認してから重みを選び、失敗した途中の重みを最終成果にすり替えない。

ガードの定義域超過、浮動小数点端点の丸め、物理的な過速度を区別する。軽微な丸め補正を、大きな過速度を無視する理由にはしない。
