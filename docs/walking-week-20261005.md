## モデル・トルク・起立を分けて準備する

現キットの `model_149.pt` は第28回Aの歩行用モデル。74入力、128→128→64→12出力、35,148パラメーターのActorとSwingCoreを使う。低い箱から起立する能力は実証していない。初回は支持下で歩行モデルに合った立位姿勢と荷重設定を作り、その後に歩行へ進む。

**100%は目標角の混合率であり、トルクの大きさではない。** トルクはKp・Kd・位置差・速度差などによって変わる。小混合の箱上試験の成功から、全量目標や全重量支持を推定しない。10%の限定候補を30%・50%・100%へ書き換える方法ではなく、既存の正式プロファイルを準備する。

リポジトリー直下で、次はファイル準備だけを行う。候補は未承認のまま作成される。

```bash
PYTHONPATH=runtime python3 -m singularitydog_hw.policy_live_profile \
  --write-template /tmp/dog-formal-v3-candidate.json \
  --template-schema singularitydog.supported-policy-profile.v3
PYTHONPATH=runtime python3 -m singularitydog_hw.policy_live_profile \
  --check /tmp/dog-formal-v3-candidate.json --plan-only
```

校正・IMU・モデル・現起動の診断から候補を組み立てる処理は [prepare_supported_profile.py](../tools/prepare_supported_profile.py)。今回、正式候補にも高速設定を保存できるよう修正した。`group-settings` の `run_settings` に `model_backend=scalar_step_cpp`、`voltage_overlap=true`、`voltage_pipeline=false`、`native_batch_encoder` のbundle相対パスとSHA-256を明示し、CLIへ `--profile-schema singularitydog.supported-policy-profile.v3` と `--scalar-step-manifest` を指定する。元モデル、scalar資料、診断、encoder実binaryを照合し、無出力計測と実出力で一致させる。高速経路の指定漏れで標準モデルへ戻さない。候補の作成は実出力承認ではない。

既存の `voltage_pipeline=true` 経路は正式設定でも通常3秒までの制約がある。回復・停止を含む地上10秒候補は、まず **scalar＋overlap＋C++ encoder、pipeline=false** で準備する。この経路にも今回の取得・電圧待ち最適化が適用される。20msに収まるかはJetsonで測定する。長時間pipelineを使う場合は別途実装と検証が必要で、今回その上限は解除していない。

立位から歩行は、既存の [ground_trial_plan](../runtime/singularitydog_hw/ground_trial_plan.py) → [ground_trial_output](../runtime/singularitydog_hw/ground_trial_output.py) → [ground_trial_review](../runtime/singularitydog_hw/ground_trial_review.py) を使う。段階は `supported_stance → partial_load → stand → walk`。`stand` と `walk` は正式な全量モデル設定と前段階の実測記録を要求する。別の判定ツールは追加しない。

現在の地上試験ツールは全体10秒以内、歩行活動1〜5秒、前進速度0.05m/s以下の有限試験を扱う。開始ランプ、停止、支持復帰の時間を含む計画を検査する。速度×時間だけで実移動距離を算出しない。同じ正式設定の前段階記録を使い、ゲイン・混合率・コード等を変えたら影響する段階を再確認する。

## 実機作業をまとめて速く進める

- Jetsonの安定給電、QDDの充電済み電池、録画、遮断位置を先に整える。通信復旧と再起動に時間を使う回数を減らす。SSHの往復時間はローカルCAN周期と別に扱う。
- 起動・電源・姿勢・ソースが同じ間は、識別・校正記録を再利用する。新しい実行の入力鮮度、電圧、STOP、現物観察は保存する。変更した部分だけ再照合する。
- 同じ試験IDへ、原ログ、ソース・設定ハッシュ、動画、音声合図、操作者観察をまとめる。一回限りの古いランチャーを再利用せず、新しい非公開保存先を使う。
- 荷重移行は全重量を受けられる補助者か固定した受けを用意する。受けを残した場合、実際に人・受けが荷重を支えていない区間を確認して自立と判定する。
- 支持付きの小試験で省略したUSB物理切断確認を、地上歩行の合格へ流用しない。支持限定の `command-loss-only` や `post_reply_deadline_policy` の例外も正式地上設定へ引き継がない。既存地上判定が要求する停止保護の証拠を揃える。

## 保存済み欠落ログの解析方法

生ログはGit外へ保存する。`DOG_REPLY_REPORT` と `DOG_REPLY_SHA256` に対象のパスと、その原本のSHA-256を設定し、次を実行する。シリアルポートやネットワークへは接続しない。

```bash
PYTHONPATH=runtime:. python3 tools/analyze_motor_reply_failure.py \
  --report "$DOG_REPLY_REPORT" --expected-sha256 "$DOG_REPLY_SHA256"
```

結果はホスト送信・受信の観測と停止の曖昧さを示す。生フレーム、UID、起動識別値、非公開パスは出力しない。返信なしという観測からCAN側の欠落と断定せず、受動USB記録と組み合わせる。解析だけで実出力許可やSTOP成功を作らない。
