# 再起動後の角度・速度の読取り診断

0.9ms間隔のr28・r29は、停止した周期まで通信返信が揃い20ms以内だったが、ゼロゲイン中にID4・ID6の角度と速度が増加して監視停止した。再起動後のr30では、有効化せず10秒間読取りを行い、全12軸の角度幅は最大0.02552°だった。r31のType17／STOP返信比較ではID4・ID6が各3回とも静止候補の一致判定となった。有効化中の変化原因は引き続き未確定。

STOP返信はr28 ID4で最終周期終了から100.084ms後、r28 ID6で149.631ms後、r29 ID6で146.937ms後に受信した。Type2を既存のRS05設定で復号した値であり、動画で検証した実角・実速度ではない。操作者の回答は現物異常なしだった。**全軸のmode0返信確認と、関節が静止したことの確認は異なる。** 小角度の変化という先の集計は周期中までを対象とする。

r29 ID6の最終2標本の角度差分は＋0.351669°／10.867252ms、区間平均0.564797rad/s。速度値だけの孤立した突出とは扱えない。Type1送信はKp/Kdとも0、目標角固定、速度・FFのraw値32767だった。FFの公称ゼロは対称16bit表現の量子化で約−0.000083925Nm相当になるが、実FWでの扱いと今回の変化原因は未確定。これを原因と決めて指令を書き換えない。

## 読取りツール

[stationary_readonly_capture.py](../runtime/singularitydog_hw/stationary_readonly_capture.py) は、前後2バスを別のスレッドが専有し、全12軸のUID照合後、角度・速度・電流・制御モード・電圧を10秒間、各軸50回取得する。

- Type0・Type17の正規読取りだけを許可。有効化、STOP、Type1、パラメーター書込みは送らない。
- 200msより短い間隔で追い付き取得をせず、返信欠落時は再送せず部分記録を残す。
- 起動ID、ポート対応、UID、読取り時刻、元の受信データ、ソースハッシュを保存する。
- 読値に変化があっても採取結果として残す。駆動承認や静止証明へ自動変換しない。
- `run_mode=0`は制御方式の読値であり、STOP状態の証明には使わない。

8件のオフライン検査で、3012要求の完了、UID不一致、途中タイムアウト・再送禁止、各バスの単一所有、有限時間・追い付き禁止、終了境界、残留バイト、非読取り指令の拒否を確認した。承認レビューのクレジット不足による実行前の中断は復旧し、Jetson上で8ファイルのソースハッシュを照合してr30を実施した。
