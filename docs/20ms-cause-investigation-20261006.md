# 10月6日夜：20ms超過の原因調査と修正

**最新のr49実測：無出力の定常1,000周期で、取得→実推論→12軸STOP代理返信→後処理がすべて20ms以内になった。** 送信間隔0.90ms・20ms期限は維持。初回1周期は別に残し、2回の定常500周期の最大は19.856942／19.788521ms、処理超過・予定期限超過・周期スキップはともに0だった。原通信・実入力・固定ソース・設定復元を独立照合した。実Type1出力、荷重支持、自立、歩行の確認は残る。

送信間隔は希望に合わせて**0.90msへ戻した**。制御周期は20msを維持する。0.85〜0.90msへの変更だけでは同条件の再試行で20ms超過が再発したため、通信返信の遅れ、推論・検証のCPU処理、native終了後の合流を分けて記録する。初回1周期、定常の処理時間、周期開始間隔は別に扱う。

この調査のCAN計測はすべてモーターを有効化しないSTOP代理診断。学習目標・正のゲインは送っていない。診断の成功を実Type1の時間保証や荷重支持の成功へ置き換えない。

## 遅れた区間

R27の後側ID12は、要求からhost読取り完了まで5.222msで、完了周期の中央値2.793msより2.428ms長かった。読取りsyscallの前後は約5µsで、前回読取り終了から次回開始まで約4.452ms空いた。取得が遅れた結果、出力nativeの開始が約15.08msへずれた。出力native本体の約7.31msは通常に近い。

R28では電圧返信が周期開始から約11.623msまで遅れ、出力native開始は約13.00ms。新しい失敗トレースでは、電圧の合流区間がwall0.996ms／main-thread CPU0.779ms、推論終了から両出力submit完了までwall1.336ms／CPU1.122msだった。GIL待ちだけを原因とせず、CPUで処理した時間と待機した時間の両方を残す。

R29の再試行は電圧合流が通常に近い一方、出力後側の通信が約1.58ms長かった。ID12の要求から返信まで4.332msで、完了周期中央値2.801msとの差は約1.53ms。最後のread syscall自体は約4.6µs、前回read終了から次回開始まで約3.50ms空いた。最初の501周期成功と、この再試行の失敗を両方残す。

R31では後側の取得が約1.32ms長く、ID12の要求〜返信は3.917msだった。出力開始が約13.37msへずれた一方、出力通信自体は7.505msと通常に近い。R34の失敗周期は全26返信が20ms以内、後側native終了も19.947745msだったが、結果を受け取る側は20.076773msで停止した。期限判定時のFuture完了時刻は保存されていないため、期限前に結果を受け取れたとは扱わない。

R34時点の待機は最大200µs刻みで、残時間が200µs未満になると次の確認を期限ちょうどへ予約する。この最後の確認機会を失う構造を修正し、期限まで400µs以内は最大50µs、さらに残時間の半分で確認する。期限の延長や期限後の成功扱いは行わない。失敗時には最後の待機要求・復帰・実際の判定時刻を別々に記録する。R34の原因だったかは新ソースの実測で確認する。

これらはhost時刻である。CAN線上、QDD内部、USB基板、USBドライバー、OSのどこで遅れたかはまだ分離できていない。C++通信関数はGILを解放して走るため、その関数内のread間隔をPythonのGIL待ちと断定しない。

- [C++相対待機の修正と比較](../runtime/experiments/native_transport_fresh_wait/README.md)：boot確認にかかった時間を待ち時間へ重ねない。待機直前の実時刻から、元の絶対wake／期限までの残時間を計算する。既存期限、キャンセル、再送禁止は維持する。
- [実出力C++にも同じ修正](../runtime/experiments/native_active_transport_fresh_wait/README.md)：交換中の相対待機を修正し、部分書込みの曖昧さ・停止確認・session所有を維持する。旧ソースをfixtureとして保存し、偽syscallで両版を比較する。
- [保存入力によるモデル比較](../runtime/experiments/native_policy_overnight/model_call_fastpath/saved_input_profile.py)：実501周期の6入力をそのまま再生し、現スカラー版とC++融合候補の目標・actor出力・観測・全内部stateを比較する。CPU演算のprofileは速度計測と別に記録する。
- [STOP入力の直接復号候補](../runtime/experiments/native_stop_snapshot_decode/README.md)：12軸分の24個のFrame生成を省くファイル専用実験。snapshot・時刻・失敗理由を保存し、Type17や実出力には選択されない。

## C++から直接完了を通知する候補

[2本のC++常駐threadを使う実験](../runtime/experiments/native_phase_owner_prototype/README.md)を作成した。各系統の取得・電圧・STOP代理段階を同じthreadが順番に所有し、固定した数値領域とnativeの完了通知を使う。模擬pipe通信の37件と、独立した寿命・割込みの16確認を通過した。作成直後と終了直後の割込みで資源が残る／古い参照を使う問題も修正した。

JetsonのLinuxでも37件すべて合格し、2世代・12件の模擬返信、両threadの終了とFD解放、18生成物のhashを照合した。実行用ラッパーでは、`/proc` の起動IDへ64MiBの読取りを要求するとENOMEMになる問題を切り分け、4KiBへ限定して修正した。CAN欠落の原因ではない。

現在は専用の模擬packetだけで動く。実CANの交換関数との接続、既存codec・失敗時処理との一致、実機20msの短縮量は未検証。通常の実出力をこの候補へ切り替えてはいない。
