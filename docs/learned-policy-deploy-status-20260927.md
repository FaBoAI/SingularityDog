# 学習済みモデル実機投入の残件（2026-09-27）

Jetsonを再起動した後の起動ID `aa9a7572-2bdc-4c18-81f9-0005e71c9fcb` でも、前後2台のUSB2CANを使って12軸をType0/17だけで読み直した。交換後の12 UIDは一致し、12軸ともrun mode 0・読取り電流0 A、最低電圧38.177 V、3回の角度読取り幅は最大0.0142°だった。ただし直前の起動に比べて各軸の生角は−19.367°〜+14.352°変わっており、旧起動の姿勢や角度枝を現起動へ無条件に引き継げない。原記録はJetsonの `RO-motor-epoch-current-boot-20260927-r2.json`。この読取りだけでモーターのSTOP返信や物理的なゼロ位置は証明されない。

同起動のIMUを10秒記録したところ970サンプルで、センサー座標の加速度ノルム平均10.679 m/s²（9.80665 m/s²に対し+8.895%）だった。計測設定の復元は確認済みだが、機体座標への取付変換・加速度補正・静止状態の現物確認は含まない。原記録はJetsonの `RO-imu-current-boot-20260927-r1`。後段の`r1`付き20周期CANベンチマークは**再起動前**の起動 `bf324501-a331-4fd0-80e8-c456baae6172` で取得した値である。

現起動でも前後2バスの20周期・位置速度24値の読取りを再測定した。両バスの開始同期と`select`受信を使っても、最古要求から最後の返信までは中央値20.748 ms、最大22.964 ms、20周期中19周期で20 msを超えた。全要求への返信は揃い、両ポートは閉じた。IMU・推論・目標送信を足す前の値である。原記録は `RO-dual-can-current-boot-sync-20260927-r2`。

保存済みカメラL字角との生角の直接比較では、現起動のID3のみモデル範囲を外れる（候補角−362.373°、範囲±28.648°）。操作者はL字記録以降にID3出力軸が実際に一回転していないと確認した。したがって`−2π`の**比較用仮説**では候補角約−2.373°となるが、元の生角を書き換えず、モーター電源区間の証拠と同一姿勢の照合が揃うまでは校正・実出力の承認に使わない。他11軸は仮符号と公称L字角による数値範囲内で、符号・原点の物理的精度は依然未確定。

前後2台のCANとIMUを同時取得して学習モデルへ単発で渡す無出力ツール[`dual_policy_once.py`](../runtime/singularitydog_hw/dual_policy_once.py)を用意した。初回の実入力試験は20周期CANとIMU 25件を保存でき、CAN取得区間は中央値28.513 ms/最大36.064 msだった。ただし旧校正候補ではID1/9/10がモデルの関節範囲を外れ、推論前に停止した。これは実際の関節故障を示すものではなく、旧校正候補が今の生角枝・姿勢に一致しないことを示す。原記録は `dual-policy-once-current-boot-20260927-r2`。この試験はシリアル受信方式、前段の20周期比較は`select`受信方式なので、差をIMUの負荷だけに帰さない。

比較専用の[`offline_camera_l_current_boot_range.py`](../tools/offline_camera_l_current_boot_range.py)は原記録を変えずにID3の`−2π`仮説を別コピーで計算し、12軸すべてが**数値上**モデル範囲に入ることを示した。出力は`/private/tmp/fabo-camera-l-current-r2-private/review-r1.json`で、起動跨ぎと40 V電源区間の証拠、物理的な符号・ゼロ、荷重時の動作は未検証と記録している。

その結果から[`offline_camera_l_policy_candidate.py`](../tools/offline_camera_l_policy_candidate.py)で無出力専用の校正候補を作り、現起動で`dual_policy_once.py`を再実行した。前後CAN各20周期とIMU 20件が揃い、IMU設定は復元され、74入力から学習済みモデルの**単発推論が1回成功**した。入力角は直前のr2角から各軸±0.01°以内、モデル目標12値は数値上の関節範囲内で、現在角との差の最大は23.49°だった。これを直接の実機移動量として使わない。原記録は `dual-policy-once-current-boot-20260927-r3`。両バスの`select`受信でもCAN取得区間は中央値28.737 ms/最大41.636 msで、20 msに届いていない。この数値は**推論と指令送信を含まない**。報告には`learned_target_sent=false`、`calibration_verified=false`、`motor_power_epoch_attested=false`を保持している。

この統合r3ではCANとIMUは並列だったが、前後CANの**各周期の開始同期**を指定し忘れ、開始ずれが中央値7.494 ms、最大19.263 msに蓄積していた。`dual_policy_once.py`で既存の`paired_cycle_sync=True`を使うよう修正し、同じ起動で無出力再測定したr4では、開始ずれが中央値0.077 ms/最大0.602 ms、CAN取得区間が中央値22.183 ms/最大24.720 msになった。r3比で中央値6.554 ms短縮。全20周期で両バスの返信が揃い、IMU24件と単発推論も完了、IMU設定の復元とワーカー終了を確認した。原記録は `dual-policy-once-current-boot-20260927-r4`。それでも18/20周期でCAN取得だけが20 msを超え、連続50 Hz、推論・送信込み20 ms、校正・実出力は未検証。関連するローカルの41テストは通過。

Jetsonのプログラム・原ログ・モデルをMac側のGit管理外スナップショットへ保存し、[`compare_dual_policy_saved.py`](../tools/compare_dual_policy_saved.py)でr4の保存済みCAN/IMU入力から単発推論を再計算した。74入力・目標角などは一致し、CPU間のTorchScript演算で`actor_residual12`だけ最大7.153×10⁻⁷の差が出た。比較器はこの欄だけ絶対差10⁻⁶まで許し、ほかの保存値・計算値は厳密一致を要求する。固定履歴仮説`h=0`と`h=1`による目標角差は最大約0.000147°で、この単発姿勢ではほぼ同じだった。これは荷重履歴の実測や物理校正を意味せず、学習済み目標をモーターへ送っていない。Macの派生記録はスナップショット内の `analysis/dual-h-sensitivity-r4.json` に保存した。

Jetson再起動前の起動 `bf324501-a331-4fd0-80e8-c456baae6172` で、箱が胴体を支える姿勢の全12軸をType0/17のみで再読した。12 UIDは交換後の記録と一致、最低電圧38.282 V、各軸3回の位置読取り幅の最大0.0142°。直前の別起動の箱上記録との差は全軸±0.02°以内だった。ただし実物の厳密な同一姿勢・モーターSTOP・原点/符号の確定を、この読取りだけで証明しない。非公開原記録はJetsonの `RO-motor-epoch-current-boot-20260927-r1.json`。

同起動の前後2バス無出力20周期（12軸Type17位置・速度）の最古要求から最後の返信までは、独立開始で中央値21.247 ms/最大27.069 ms、開始同期を入れて中央値20.396 ms/最大23.838 msだった。前者は20周期中15周期、同期後も13周期で20 ms超。各バスの12要求送信幅は約17 ms、末尾返信待ちは約2.7 msで、設定した送信間隔0.5 msに対する実測の書込み終了→次の開始は中央値約1.0–1.1 msだった。いずれもIMU取得・74入力組立・モデル推論・12目標送信を含まない。非公開原記録は `RO-dual-can-current-boot-20260927-r1` と `RO-dual-can-current-boot-sync-20260927-r1`。したがって50 Hz全工程の達成は未確認で、今回のType17個別問合せ経路は読取りだけでも予算超過がある。

送信間隔を0 msへ単純に縮める案は以前の[実機読取り比較](can-pipeline-probe.md)で返信欠落が起き、0.25 msでも欠落しているため、同じ条件を高速化の実績とは扱わない。前後2バスの開始同期はずれを減らしたが、返信処理とシリアル待ちも残る。20 msの次候補は、制御指令のType2複合返信または自動報告から位置・速度を受け、別々のType17問合せを省く構成。ただしType2の速度換算・鮮度、自動報告の複数台開始/解除、故障停止と実送信を実機で照合する必要がある。

今日追加した[`motor_epoch_readonly_capture.py`](../runtime/singularitydog_hw/motor_epoch_readonly_capture.py)は現起動の12 UID・生角・電圧を一括保存する読取り専用ツール。[`motor_power_epoch_manifest.py`](../runtime/singularitydog_hw/motor_power_epoch_manifest.py)は、同一起動における投入前後2記録と、操作者の40 V Off/On・外部電圧/実物観察を結び付けて角度枝を比較する。いずれも原点変更やモーター出力を行わず、電源状態・STOPの独立検証を称しない。Mac/Jetson双方の新規テスト9件は通過。

残件の順序は、(1)ID3/9の電源跨ぎ角度枝とID10を含む12軸の符号・原点を実物へ照合、(2)箱を残した少量の荷重移行用にクリアランス・トルク・電圧と停止復帰を検証、(3)学習モデルの74入力→12目標を同一電源区間の生角へ変換し、滑らかな切替・STOP・watchdogを持つ実出力ランナーを構築、(4)IMU・12軸取得・推論・送信の連続50 Hzを実測、(5)独立した落下受けまたは補助者を用いて自立・歩行を段階的に試すこと。現在は**実CAN・IMUを合わせた74入力による単発の無出力推論**と、別試験での**箱上12軸の現在位置保持**まで確認済み。両者を結ぶ実出力経路は未完成。

時間の目安は、現起動の単発無出力入力照合が完了した段階から、箱上の荷重移行と固定立位に好条件で追加5〜11時間、学習モデルの実出力・連続50 Hz検証にさらに1〜3作業日。ただし同期後も取得だけで中央値22.183 msなので、20 ms周期を満たす通信経路の再設計・実測に要する時間はこの範囲へ含めない。自立試験には独立した受け止め手段が必要で、現状の一人作業・箱のみでは開始時刻を見積もれない。
