# 9月25日の検証計画 — Active Reportingと20ms制御

**今日の主目標は、RS05の自動報告で毎周期の読出し要求を省き、前後12台・IMU・単一方策推論・送信を組み合わせた時間を測ることです。** まずモーターを駆動しない条件で検証し、20ms未達なら残った最大の遅延要因と次の修正を確定します。

作成日：2026-09-25。これは実施計画で、試験結果ではありません。計画作成時点ではJetsonへの接続・転送・設定変更・実機送信を行っていません。

その後の実施結果は[自動報告の実機検証記録](hardware-active-reporting-20260925.md)へ分けて記録します。

## 出発点

最新の統合測定は独立した単発3回です。並列取得の中央値14.483ms、入力組立3.671ms、入力検査・推論・結果変換9.642ms、最初〜最後のホスト送信9.467ms。最古入力の取得開始から最終ホスト送信までは中央値37.780ms・最大39.089msで、20ms未達です。個別中央値の合計を全工程時間にはしません。

この送信は全ゼロType4停止命令による代理測定で、学習した目標角を送った結果ではありません。現在の受信実装は要求に対する返信を扱うため、自動報告を有効にするだけでは置き換えられません。

時間は準備実装60〜90分、実機確認と集計50〜70分、合計約2〜3時間を最初の見積りとします。未知のFW動作・実装不具合の修正は追加です。20ms達成や今日中の歩行を保証する時間ではありません。

## 最初に開発側で準備するもの

- 前後の各ポートを1つのI/O担当だけが所有し、連続受信と指令送信を管理する。IMUは別担当で取得する。
- Type24の開始／解除と、必要な場合だけ`EPScan_time (0x7026)`の読出し／変更を許容する専用試験経路を用意する。既存の読取り専用制限を一括解除しない。Type1駆動指令・Type3励磁・原点変更・ID変更・保存・FW更新はこの試験に含めない。
- ID別の固定サイズ記録に、生フレーム、受信区間、ホスト受信番号、変換版を残す。ログ整形・ハッシュ計算・ディスク書込みを周期外へ移す。ログ領域は上限を設け、あふれを検出する。
- 受信の分割／連結、未知の型・ID、DLC不正、古い標本、片側の受信停止、fault、設定途中の例外、終了時の復元失敗を模擬する。Type2とType24のどちらが返っても無条件に通す実装にはしない。
- 推論は事前warmup済みの1方策を使用する。連続試験では内部状態を周期間で維持する。負荷履歴hの仮説・換算候補は診断用として明記し、実機制御用に確定したものとは扱わない。

この準備中、操作者が脚をL字に保持する必要はありません。実行用コマンドは実装・事前検証が終わってから提示します。

## 実機試験の内容

### 1. 開始時の確認をまとめる

JetsonとMakitaの給電、前後USB2CAN、全12個体、FW、電圧、故障／動作状態、IMU、競合プロセスを1回で確認します。直近の記録を再利用し、全脚の校正は最初からやり直しません。支持台と脚の離隔、即時40V Offの条件も開始時にまとめて確認します。

周期パラメーターとIMU設定は変更前に読取り保存します。Active ReportingのON/OFFには確実な読戻し方法が未確定なので、元状態が不明ならそれを記録し、今回の試験を開始できる既知の状態を先に確定します。既定OFFを元状態だったとみなしてはいけません。

### 2. 1台・10ms報告を確かめる

最初は前側の1台を対象に、Type24で報告を開始します。RS05資料上の既定は10ms、`EPScan_time=1`です。既に1なら周期設定は変更しません。異なる値から変更する場合は元値を記録し、読戻しと実周期を照合します。

- 最初の短時間で送信元・宛先・型・DLC・mode・faultを確定し、成立後に10秒→60秒の有限記録へ進む。
- RS05資料内の「返信Type24」と「報告Type2」の不一致を、現物FWと生フレームで解決する。
- 静止時の位置などを個別読出しと照合する。個別照合の通信を性能測定区間から分離する。
- 静止値だけでは速度倍率・トルク換算の正しさを証明できない。これらは実駆動へ進む前の残条件として扱う。
- Type4を送った後も報告が継続するかを別区間で確認し、Type24の解除で周期報告が止まることを確認する。

無駆動状態で報告できない場合、確認のためにその場で励磁せず、対応FW／プロトコルの切り分けへ移ります。無駆動でもType24／18による設定送信は伴います。

### 3. 6台ずつ、最後に12台を受信する

前6台だけ→後6台だけ→前後12台の順で、各条件10秒→60秒を測ります。CAN・UART設定、CPU設定、ログ方式は固定し、同時に報告周期やUSB書込み方式を変更しません。

最初の比較は10ms報告です。各IDの受信間隔p50／p95／p99／最大、20msを超える更新空白、予想件数との差、パーサーエラー、受信キューの増加、CPU負荷を残します。**内部連番がないため、件数が揃っただけで物理通信の欠落ゼロとは断定しません。** 静止中に同じ数値が繰り返されても、それだけで重複フレームとは判定しません。

次へ進む最初のホスト側基準は、全対象IDが揃い、mode0／fault0、解析失敗ゼロ、20ms超の更新空白ゼロ、バッファ滞留の増加なしです。これは今日の無駆動比較用の条件であり、歩行に許容できるセンサー遅延を確定する条件ではありません。

### 4. 全工程の50Hz測定

常時受信している前6台・後6台とIMUから、同じ20ms周期で入力をまとめます。12台とIMUの更新番号、元の受信／取得区間、入力採用時刻を保持し、単一方策を推論します。推論した目標は記録だけに残し、送信は従来と同じ全ゼロType4停止命令の代理測定とします。

この統合区間では自動報告とSTOP応答が更新を補い合う可能性があります。結果は混在した状態フィードバックのホスト観測性能として記録し、自動報告単独の継続・更新品質は段階3の記録で判定します。

最初の10秒が成立した条件だけ60秒へ延ばします。周期に間に合わなかった処理を後からまとめて送信せず、その試験を不成立として終了します。入力がモデル範囲外なら切詰めて通さず、入力評価と通信性能評価を分けます。必要な姿勢補助はその段階で短時間だけ依頼します。

| 判定対象 | 測るもの・今日の基準 |
|---|---|
| 50Hzの処理期限 | 周期の予定開始→最後のホスト書込み完了が全周期20ms以内。p50／p95／p99／最大、期限超過数を報告 |
| ホストで観測した入力の古さ | 採用した最古の元受信／取得区間開始→最後のホスト書込み完了が20ms以内。入力採用時と送信時の年齢、12台＋IMUの時刻差も報告 |
| 周期ごとの更新 | 全12台とIMUの新規受信／取得を確認。古い値の使い回し・補完・時刻の付替えで合格にしない |
| 受信と終了 | 全対象の状態を確認。fault、解析失敗、受信期限超過、滞留増加があれば不成立。停止応答確認は下記の別区間で行う |

**自動報告にはモーター内部の採取時刻がありません。** 新しいホスト受信時刻が新しい物理標本の時刻とは限らず、CAN・USB・OSのバッファ遅延を含みます。上表を満たしても「ホスト観測ベースの20ms代理測定」と記載します。旧方式の取得開始からの時間と直接同一視せず、報告周期と滞留の観測を併記します。実採取→CAN線上の指令完了という厳密な全工程の遅延は、内部時刻・転送遅延の根拠が揃うまで未判定です。

### 5. 自動報告とSTOP応答を取り違えない

報告がType2の場合、同じIDのSTOP応答と形式が同じで要求番号がありません。**STOP送信後に来た最初のType2を、そのSTOPのACKとして集計しません。** 自動報告中は送信時間と状態観測の鮮度を測り、「最後の返信まで」の旧指標は同じ意味で作りません。

STOPへの返信確認は別区間で、自動報告を解除→有限時間の残留排出と静穏確認→Type4送信→対象の返信確認、の順に行います。静穏を確立できなければ応答対応は未確認です。報告中のmode0は停止状態の観測であり、特定のSTOP指令の到達証明ではありません。

終了時は変更した周期とIMU設定を復元・読戻しし、報告状態を既知の開始状態へ戻して確認します。ONだった状態へ戻す場合は、その配信再開も確認します。例外時も同じ終了処理を実行し、復元不明を成功に含めません。I/O担当の終了、ポート閉鎖、排他の再取得、結果保存までを確認します。

## 20msに届かなかった場合の修正順

1. **送信側が遅い：** 前6台／後6台の指令を事前準備し、現行1フレーム書込みと2→3→6フレームのまとめ書込みを比較する。これは追加20〜40分以上の実機比較と実装時間を別に見積もる。連結処理・部分書込み・期限・停止までのキューを確認し、初回から未検証の6台一括を採用しない。
2. **入力組立が遅い：** 再デコード・コピー・証跡整形を削り、受信時に作った固定記録を渡す。ID・故障・鮮度・範囲の動的判定は維持する。
3. **推論が遅い：** 通信と同時実行した条件でテンソル再利用・CPUスレッド設定を比較する。保存入力での高速な結果を実入力の結果として扱わない。
4. **受信の滞留が残る：** バス別・USB別・IMU別に分ける。Type1への状態返信と自動報告が将来重複する負荷も評価し、必要ならCANopen SYNC／TPDOやSocketCAN機器を別比較にする。今日の初回計測でプロトコルを切り替えない。

1回の比較では1項目だけを変え、最初の統合結果に対する差を記録します。再起動原因調査は既存の指定どおり今回の対象から外しますが、再起動が起きた測定を完走扱いにはしません。

## 今日の終了時に残すもの

- 個体・FW・ソフト・モデル・校正候補・設定値の対応と、試験条件ごとの生記録。
- 1台／前6台／後6台／12台／統合の比較表。更新空白、入力年齢、時刻差、期限超過、復元結果を含める。
- 20msの判定を「周期処理」「ホスト観測ベースの遅延」「物理採取からの遅延」に分けた結論。
- 残った最大の遅延と次の修正1件。実駆動へ進む場合に残る校正、速度換算、IMU、負荷履歴h、全12軸の共通停止・保持条件。

今日の20ms試験に合格しても、直ちに歩行合格とはしません。上の実出力条件を揃えた後に、支持下の有限な全脚保持→固定立位→学習方策への切替という順で進めます。
