## 失敗と復旧の記録

1. 3フレーム条件は欠測を検出した時点で追加送信を禁止し、ポートを閉じて排他を解放しました。自動再送はありません。
2. 独立した全12台の確認でも前側ID1の識別返信がなく、中断しました。後側はID7〜12の識別を取得後、前側の失敗により続行せず終了しました。両ポートの閉鎖・排他解放を確認しました。
3. ユーザーが40VをOffにし、前脚側USBを抜き差し、40VをOnに戻しました。
4. 同じJetson起動・前後by-pathで、全12台の個体照合、電圧、周期値の読取り、STOPのmode0／fault0返信、前後各100ms静穏が成立しました。両ポートを閉じ、排他を解放しました。自動報告の再有効化や周期変更はありません。

3フレーム送信の後に通信が失われましたが、ホストログだけではアダプター・CAN線・QDDのどこで止まったか確定できません。USBとモーター電源の両方を操作して復旧したため、USB単独の故障と断定もしません。

## 受信区切りとホスト処理の手掛かり

2フレーム条件の各組と3フレーム条件の受信は、いずれも32バイト＋2バイトでした。2番目の返信は、本体の大部分が最初の32バイトに入り、残りの終端2バイトで完成しています。完成時刻には約2.5〜2.6msの差がありますが、これをCAN線上の返信間隔とは扱いません。

実機の両CH340はUSB 12Mbps、`ch341-uart`ドライバ、Bulk IN／OUTの最大パケット長が32バイトでした。受信区切りと整合しますが、成功した34バイト送信も失敗した51バイト送信も32バイト境界を跨ぐため、境界だけで失敗を説明することはできません。

また、最初の32バイト受信完了から次の読取り処理へ入るまでにも約1.27〜1.38msあり、全量がUSBの待ちではありません。独立したポートを開かないCPU測定では、起動IDの読取り約0.061ms、ポート結付け確認約0.072ms（各100回の中央値）でした。現在は受信ループの複数層からこれらを繰り返すため、次は確認処理の重複と実際のI/O待ちを分けて計測します。このCPU測定は別実行なので、実機周期の費用としてそのまま差し引きません。

正常な受信経路のコード確認では、前の受信完了→次の上位読取り入口に4回、その入口→`os.read`直前にも4回の起動ID・ポート確認があります。後半の約1.24〜1.27msも、確認処理と`select`を含む上位APIの区間であり、USB単独の待ち時間ではありません。別測定の中央値を機械的に当てはめると各4回で約0.53msですが、実際の区間内訳を測定した値とは区別します。

## 次の対策

- 3／6フレーム連結を制御経路へ採用しない。2フレームも候補段階に留める。
- 従来の1フレームずつ送る方式で、送信前の準備・受信処理・実行待ちを分けて計測し、フレーム間隔を確保したまま余分な処理を減らす。
- CAN線上の受動観測または別アダプターで、ホスト書込み後の欠落箇所を切り分ける。今回の失敗を再送で成功扱いにしない。
- 証跡収集も改善する。共通受信器には`os.read`直後の期限・取消例外で、読めたバイトが呼出し側の生ログへ渡らない経路がある。今回の通常の250ms欠測の説明にはならないが、例外時のバイト保持を修正候補にする。250ms以後の遅延返信は今回観測していないため、必要なら元の失敗判定を維持した有限の受信専用追跡を追加する。
- [Active Reportingの開始・解除失敗](hardware-active-reporting-20260925.md)は別に解決する。入力組立ての約14%短縮も含め、取得・推論・送信を接続した全工程で再評価する。
