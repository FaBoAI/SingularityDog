# 送信間隔0.8／0.7／0.6msの有限比較 — 2026-09-25

**未返信上限を各バス3件に固定した通信単独の比較では、0.6ms条件が取得中央値7.723ms・最大8.095msで、3回とも欠測なく完了した。** 同じ比較の0.8ms条件から中央値0.977ms短縮した。IMU・推論・後段送信を含む全工程20msの達成を示す測定ではない。

前後6台ずつを並列に取得し、全12台のUID確認後、全0のType4停止命令へ返るType2を各条件3周期測定した。各起動は48個の個別17バイトwrite（UID12・STOP36）と48返信。CPUは既存729,600〜1,497,600kHzの上下限内で一時的にperformance、受信方式・プログラム・イベント記録方式は3条件で同じ。モーター有効化・目標値送信・自動再試行は行っていない。

取得時間は最初のSTOP write開始から全12台の最後の返信まで。ホストwrite区間は最初のwrite開始から最後のwrite復帰までで、CAN線上の送信完了とは異なる。0.6ms条件のホストwrite区間は0.8msより中央値0.923ms短い。0.6ms条件の実際のwrite復帰→次write開始は、前バス中央値0.757ms・最短0.729ms、後バス中央値0.732ms・最短0.722msだった。

保存した生バイト・フレーム・返信対応・時刻を既存の検証関数で再照合し、9周期の時間を再計算した。全条件で送信間隔違反なし、実際の最大未返信は各バス3件、STOP返信108件はすべてmode0／fault0。未返信・残留バイトなし、ワーカー・ポート・起動確認FDの終了と排他解放も確認した。CPUのschedutil復元は親処理・独立watchdog・外部読取りの3記録で一致し、周波数上下限も不変だった。

監督処理の最終JSONには前回の条件ラベル（上限3／4／2件、間隔すべて0.8ms）が残っていた。これは記録上の不整合として原本を保持し、証拠JSONにも明記した。実際の上限3件固定・間隔0.8／0.7／0.6msは、ハッシュ固定の子処理、各回の実行計画・結果、照合済み生ログで確認している。実行やCPU復元の失敗として扱うものではない。

各条件3周期の順次比較であり、長時間安定性やp99の保証には使わない。以前の0.5ms・上限2件の返信欠落は別条件の失敗として残る。今回の0.6msを統合工程へ反映した場合の効果は、実入力・実推論を含む別の測定が必要である。
