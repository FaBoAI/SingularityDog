# CANとIMUを同時に取得する有限診断

`runtime/singularitydog_hw/sensor_pipeline_benchmark.py` は、12関節の位置・速度を並行で読みながらIMUを取得し、20msごとに入力の古さと更新率を測ります。モデルのロード・推論・モーター駆動は行いません。現在の関節角度がモデル範囲外という問題を、通信の性能測定から分けるためのツールです。既存の方策診断の角度・鮮度判定は変更していません。

```sh
# runtimeディレクトリーで計画を表示。まだ機器へアクセスしない。
python3 -m singularitydog_hw.sensor_pipeline_benchmark \
  --expected-uids /private/path/expected-uids.json \
  --output /private/path/new-sensor-capture
```

`--execute-no-output` を付けた場合だけ実行します。既存のCAN利用者がなく、モーターが停止済みであることが前提です。読み取りで動作中のモーターを止める機能はありません。

| 項目 | 固定条件 |
|---|---|
| CAN | 個体照合12要求＋位置・速度24要求×20巡、最大492要求 |
| 並行取得 | 最大4要求、write完了から次のwriteまで0.5ms以上、全IDの位置→全IDの速度 |
| UART | 921600bps。CAN速度の設定変更はなし |
| 観測 | 20ms周期、開始遅延の許容5ms。遅れの取り戻し実行なし |
| 有限時間 | 既定10秒、初回の全入力待ちは最大2秒 |
| 診断上の鮮度 | 最大100ms・取得時刻幅100ms。実機制御の承認値ではない |
| 終了 | 20巡完了後にCANを閉じ、IMU設定を復元し、取得thread終了・ログ保存を検査 |

`events.jsonl` に実送信byte・受信byte、各要求のwrite開始／受信完了時刻、キュー到着時刻、観測値を保存します。原時刻を書き換えず、その観測時刻までに到着した値だけを使います。個体12台の一致前には位置・速度を受け入れません。欠落・重複・残留byte・書込み不足・期限超過・キューあふれは中断し、再試行しません。

更新率は、前回と**値が違うかではなく、位置・速度24項目それぞれの取得時刻が新しくなったか**で計測します。最初の観測は比較の分母から除外します。20msで観測できても、24項目が毎回更新されたとは限りません。IMU更新率も別に記録します。

成功状態`COMPLETE_SENSOR_BENCHMARK_NO_OUTPUT`は有限な取得・保存の完了です。連続50Hz制御、推論時間込み20ms、モーター指令の送信・停止の成立は示しません。CAN応答に取引番号がなく、前巡の遅延返信を同一キーの次巡と完全には区別できない限界も残ります。

## 2026-09-23の実機測定

同じ起動状態のJetsonで、各条件20巡・492要求/応答を記録した。CAN速度、UART921600bps、window4・gap0.5ms・要求順は変更していない。

| 条件 | 12関節の位置・速度1巡：中央値 | 最大 | 20ms観測で全24項目が更新 |
|---|---:|---:|---:|
| CAN＋IMU＋キュー・非同期ログ r1 | 78.473ms | 85.756ms | 0 / 71比較 |
| 同じ実機でCANのみの対照測定 | 26.023ms | 26.712ms | この条件では測定なし |

r1では72回の20ms観測を完了し、IMUは71比較すべてで更新した。関節項目の更新数は1比較あたり中央値6/24。観測の開始遅延は中央値0.567ms・最大1.325msでも、入力の最古時刻は中央値82.517ms前・最大87.412ms前だった。**予定時刻に処理を呼べることと、新しい全軸データを揃えられることは別である。** 受信欠落・ログ脱落は0、CAN終了・IMU復元・全取得thread終了・ログ保存を確認した。

対照測定は前日のCAN単独26.639msに近く、統合処理の負荷を切り分ける根拠となった。r1のCAN送信開始間隔中央値は2.572msで、最小設定0.5msより長い。毎回の予算検査でboot情報のファイルを開閉する処理は、同じJetson上の2000回測定で平均41.257μs、開いた記述子から`pread`する方法は1.579μsだった。この差だけで全遅延の原因を断定せず、確認頻度・停止条件を保つ修正を別記録で測る。

全条件は無出力。生通信データ・個体番号・接続先は非公開に保存し、公開用の集計には含めない。


### 最適化版r2は最初の識別で中断

boot情報を一度だけ開き、毎回`pread`で照合する方式へ変更した。確認頻度、停止・期限条件、CANの窓・間隔は維持し、新規19件を含む109テストと独立レビューを通過した。ファイル記述子の読み取りとcloseを同じlockで保護する。

実機でのr2は、最初のID1識別要求1件に対して返信がなく、250ms期限で中断した。位置・速度の読み取り、観測tick、推論、駆動はいずれも0。IMU設定の復元、取得thread終了とログ保存を確認した。これを高速化後の性能値とは扱わず、その時点では40V電源状態の確認が必要となった。r1・対照測定を上書きせず、自動再試行していない。

その後、USB2CANを前脚・後脚の2系統へ分割し、全12個体の照合とCANだけの同時読取り、左前・右後の短時間駆動・停止を別記録で確認した。[2系統の検証結果](dual-can-verification-20260923.md)。この結果はIMU・推論を含む本ベンチマークr2の成功を意味しない。
