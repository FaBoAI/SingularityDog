# USB2CAN調査レポートを使った最適化 — 2026年10月7日

添付レポートの提案を現物・現在のソース・保存原票へ照合した。優先するのは、現在の通信契約を保ったまま推論前後のコピーと完了通知を軽くする変更。R16〜R19は要求間隔880µs／window3、最新R20はユーザー指定890µs／window3を別の明示比較として使用し、[成功設定](jetson-best20-settings.md)の900µs基準と既定値は残す。

## 今回の変更と実測

- native完了後に作っていた追加の完了済みFutureを削減。元のnative Future、世代番号、両ownerのjoinと期限判定を使用する。
- 成功経路で不要な例外オブジェクトの生成と辞書コピーを削減。STOPのfault検査は元の符号化ビットと同値な直接検査へ変更する。
- SHA固定の保存原票から、取得・推論・最終host write・最終返信・Python joinを分けて解析する[ツール](../tools/analyze_native_pair_latency.py)を追加。
- 完了周期だけでなく、失敗した周期の元返信・時刻・部分結果を保存する。未返信や鮮度超過を成功へ読み替えない。

## 実Type1の中継削減とC++完了通知

890µs／window3／20msを維持する追加候補として、実Type1のnative pair経路から、結果を別のPythonタスクへ渡して追加Futureへ公開する中継を外す。両C++ ownerが終了した元の保存領域を、同じcoordinatorで検査・復号し、最初に作った2つのFutureへ直接公開する。元の17byte送受信、各要求の開始・送信終了・返信・期限の時刻、世代番号を保持する。通常のbus経路と、取得に続けて電圧を読み出す経路は引き続き別のownerを使用する。

専用pipeでC++処理の完了とPython結果の公開を通知し、C++の待機処理で受ける。通知だけでは返信完了とみなさず、現在の2つのFutureが完了し、復号と結果取り出しが元の期限内であることを再確認する。通知が届かない場合も200µsごと、native期限までの最後の1msは50µsごとの確認を残す。通知機能がない旧binaryでは従来の待機へ戻る。別世代のFuture・キャンセル・不正な通知ABIは成功に読み替えない。

例外経路のSTOPはnative writerの終了後にだけ送る。結果変換中からcoordinator自身の終了待ちを行わず、失敗時だけ既存bus poolへ停止処理を渡す。元の部分返信を保存し、enqueue後にFutureを受け取れなかった場合も送信なしと推定しない。

これは新ソース候補であり、R20のSTOP代理・旧R16の実Type1測定を新ソースの時間実測へ転用しない。短縮量と20msの実機結果は、同じ成功設定を記録した新しい5→501周期診断と、箱を残した実Type1で別に測る。

両方の元Futureが完了していても、最後の通知書込みと公開処理が終わる前にmain threadが起きることがある。その場合は追加の50／200µs待機へ戻らず、公開完了のEventだけを元のhost期限の残り時間内で待つ。通知の書込み失敗・期限超過は引き続き拒否し、結果の準備完了を偽装しない。native writerの終了とPython公開完了を別の状態として保持する。

## 6軸のType2復号をC++へまとめる

前後各6軸の通常Type2フィードバックを、一度のC++呼出しで復号する経路を追加した。実Type1返信と入力取得の両方で使用する。元のRecord保存領域を読み、ID・送受信フレーム・mode・faultを検査してから、既存と同じフィードバックオブジェクトと順序の辞書へ戻す。返信時刻・送信終了時刻・read開始時刻、元byte、元の所有領域は変更しない。

構造体のサイズ・全field位置と関数ABIを確認する。新機能がない旧libraryは既存のPython復号を使い、部分的なABIや不正な関数は拒否する。識別・電圧・parameter・不正／混在フレームは既存のcodecへ戻すため、拒否の意味を保持する。このC++関数は通信を行わず、6件すべてを検査できるまで出力を公開しない。

位置・速度・トルク・温度の16bit値は、全65,536通りを既存Python実装と浮動小数点のbitまで比較した。R20の元SHAを固定した501周期・13,026返信でも照合し、2,004組／12,024フィードバックの値・順序・時刻・浮動小数点bitが一致した。1,002組の電圧返信は既存経路を維持し、元bufferと保存ファイルの不変も確認した。

[部品比較](../runtime/experiments/native_active_transport/benchmark_feedback_decode.py)は12軸分の既存Python復号と新しいC++境界＋同じPythonオブジェクト構築を測る。各sampleで実行順を交互にし、trialごとに先頭の方式を反転する。保存原票の独立照合は[専用ツール](../tools/verify_native_feedback_decode.py)で再実行できる。Macでの部品時間は証拠JSONへ記録する。通信・推論・全周期を含むJetson測定ではないため、R20の時間から部品の差を単純に引かない。

他の検証と重ねずに行った4巡×2,000回の部品比較では、各巡の中央値は既存Python 68.833〜69.417µs、C++経路21.834〜22.000µsだった。差は46.917〜47.417µs。元buffer・GC状態の復元を確認し、全sampleの時間・最大値も保存した。初期比較と、保存再生のCPU処理に一部重なった比較も保持する。

最終の対象回帰459件は458成功、実Linuxのcoordinator設定を使う1件だけはMacのためskip。通知・取消・別世代・部分返信・終了STOP・全12軸の±360°不連続・復号・エンコーダー・CLI／profileの拒否を含む。途中の失敗も証拠JSONに保持した。意味の検査へ実時間の揺れが混ざった関節不連続テストは共有した因果時刻へ修正し、実時間の期限テストは維持した。また、模擬STOP装置の起動前から期限が始まるテストの問題を35msの起動遅延で再現し、装置の準備完了を待つようにした。同じ90／250msの期限と28ms返信遅延で期待する軸の返信を確認し、製品のSTOP期限は変更しない。

## 既存の12軸C++エンコーダーも検証

既存の任意選択C++エンコーダーは実装を変更せずビルドし、2,000ケースの全12軸byte一致と境界・拒否条件を確認した。検証済みloaderの96 byte比較と72拒否canaryを含む[比較ツール](../runtime/experiments/native_policy_batch_encode/benchmark_verified_wrapper.py)を追加した。Macの中央値は既存Python 48.687µs、検証済みC++ラッパー1.625µsで、差は47.062µsだった。部品ごとの中央値を足して全周期の短縮とは扱わない。

profileの任意選択とsource／binaryのSHA固定を保ち、既定のエンコーダーや承認は変更していない。MacのPython 3.13向けbinaryはJetsonへ持ち込まず、JetsonのPython・aarch64向けに再ビルドし、新しいsource・現在の起動・電源・姿勢へ結び直してから比較する。
