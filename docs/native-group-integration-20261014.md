# 4系統のType1通信をC++へ統合 — 2026年10月14日

指令計算間隔のばらつきを減らすため、周期中の4つのPython通信所有者を、同じライブラリ内の4つの常駐C++所有者へ置き換える選択肢を実装した。取得、電圧確認、実Type1送信を制御ループへ接続している。モデルの計算と動作制限は既存のものを使う。新しいソースでの実CAN・実出力の確認は残る。

## 課題と修正

| 課題 | 修正 | 状況 |
|---|---|---|
| 診断の初期化が最初の指令時刻を古くする | 診断初期化を姿勢読取り・有効化より前へ移す。C++所有者の起動後は、本当に新しいゼロゲイン返信を取得してから指令時刻を設定する | ○ 再現テスト済み |
| 4つのPython所有者の起床・GIL再取得・Future通知が重なる | 4つのC++所有者を一括で開始し、保持と電圧確認を続けて処理。Pythonは各段階で4系統の結果をまとめて受け取る | ○ ソースと制御ループ接続済み |
| 通信の遅れとPython受け渡しの遅れが混ざる | nativeの開始・終了・一括開始・収集時刻を原票へ保持。従来経路にも事前確認・submit・owner開始の境界を追加 | ○ 計測処理を追加、実機での分離は△ |
| 初期化中の停止と通信所有権が競合する | constructor中にも借用状態を登録。キャンセル後はC++所有者をjoinしてから従来のSTOPへ返す | ○ 競合・途中失敗を模擬検証 |
| 中断時の未回収返信が失われる | issued phaseを区別したキャンセル後snapshotを保存。未発行のゼロ値を返信済みとして扱わない | ○ 原票保持を検証 |
| 同一ticketの重複記録が別内容でも見逃される | rawバイト・status・count・所有者時刻・errorを照合し、矛盾時は両画像を残して不合格にする | ○ 不一致の負例を検証 |
| 要求前の期限切れが初期ticket0の返信と誤照合される | 未開始の失敗を現在ticketへ結び、未発行・未観測として別記する。初期ACKは保持し、元の期限エラーを報告する | ○ 500周期比較で発見し、実socketの再現テストで修正 |
| 終了したSessionで通常指令を再開できる | nativeとPythonの両方を終了時にpoisonし、所有権の返却後は既存の緊急STOP専用にする | ○ 全4系統のSTOPを模擬確認 |
| 古い成功記録が新しいC++版の合格へ流用される | 明示した30Hz契約、新backend名、4つのC++ソースSHA、実際の所有者設定と復元・snapshotを必須にする | ○ 旧経路との取り違えを拒否 |
| 新版での2秒・10秒の安定動作 | 新ソースの診断から同じ設定でやり直す | × 新版の実出力は未実施 |
| 荷重支持・自立・歩行 | 完走・追従確認後、準備した支持方法で段階的に確認する | × 未達 |
| 原点の絶対精度・正式なIMU校正 | 外部計測を伴う校正と最終確認を行う。速度の小さな揺れと機械的な動きを独立に照合する | △ 通信の高速化だけでは確定しない |
| 新30Hzモデルの左移動・停止保持 | 途中終了したシミュレーション2ケースを原因とともに取り直す | △ 7ケース中5ケース完了の履歴を保持 |

元の実機失敗では、32周期目の最初の要求が前周期より約0.752ms遅れ、取得区間は約0.252ms、推論区間は約0.149ms増えた。4系統の通信開始後のサービス時間は大きく変わっていない。一方、port1のnative終了からBatch時刻までの区間は約0.213→0.818msへ増えた。この区間には復号・データ準備も含むため、実機停止の原因をGILだけに確定していない。[原票解析と履歴](type1-command-gap-investigation-20261014.md)。

## 変えた通信経路

```mermaid
flowchart LR
  A[主制御: 4系統を一括開始] --> B[C++常駐所有者 ×4]
  B --> C[各系統: 前回目標3軸の保持と返信]
  C --> D[保持結果4系統をまとめて取得]
  C --> E[各系統: 電圧1軸の取得]
  D --> F[既存のIMU確認・学習モデル推論]
  E --> G[電圧結果をまとめて取得]
  F --> H[既存の原入力・動作制限・期限検査]
  G --> H
  H --> I[C++で全4系統の送信を開始]
  I --> J[各系統: 新目標3軸の送信と返信]
  J --> K[全4系統の返信を一括取得]
```

CAN配線・USB2CANは4系統、要求間隔は900µs、windowは3を維持する。1周期は各系統で保持3＋電圧1＋実出力3、合計28要求である。CANのフレーム形式を変えたり、物理的に異なるCANへ1フレームで送ったりする変更ではない。

入力鮮度と入力→全軸host書込みは20ms、返信期限は33.333334ms、指令計算間隔は34.333334ms、host watchdogは40ms、モーターの通信断設定は200msのまま。初期化の古い時刻を現在時刻へ書き換える処理や、欠けた返信を成功に補完する処理は入れていない。

## 検証の範囲

常駐所有者のC++テスト、原フレームを使うAF_UNIX模擬通信、初期化と停止の競合、期限超過・原票矛盾の負例、制御ループの正常開始・混合・停止ランプを検証する。37msの所有者起動を注入しても、起動後の新しいゼロゲイン返信で開始することを確認する。旧経路と新経路で同じモデル目標を受け取り、同じ動作制限と20msの送信期限を適用する。

CPU比較は別プロセスの仮想返信相手を使い、同じ複合ライブラリで従来の4つのPython所有者と4つのnative所有者を比較する。実機CAN・USB、実IMU、学習モデルの推論を含む周期測定ではない。ホスト上の有限比較をJetson実出力の20ms保証や荷重支持へ読み替えない。

現ソースの関連289テストが成功し、失敗・skipゼロ。公開準備・キット関連14テストも成功した。実socketの長期比較で見つかった未開始要求の誤照合も、期限を広げずに修正した。

| Mac上の仮想返信2ms・30Hz比較 | 従来のPython所有者 | 常駐C++所有者 | 読み方 |
|---|---|---|---|
| 初回・旧比較条件 | 93周期完了後に停止 | 31周期完了後に停止 | 100µs・GC延期を比較にも明示する修正と、空結果の誤照合修正前。失敗原票を保存 |
| 修正後・別のCPU検証と一部重なった比較 | 500周期完了 | 500周期完了 | 両方式の送信バイト一致、20ms書込み・33.33ms返信超過0、模擬STOP・設定復元。CPU負荷が均一でなく、性能優劣の判定には使わない |
| 修正後・その検証を終えた再比較 | 56周期完了後に停止 | 106周期完了後に停止 | 元の期限エラーを保持。両方式とも全4系統の模擬STOP・設定復元。500周期成功とは扱わない |

500周期完了した比較の、同一ポートの保持返信→電圧要求開始の中央値は、従来178.292µs、C++版5.500µsだった。一方、native出力終了→Python収集の中央値は104.792→554.625µsで、主制御側の費用が残る。途中停止した再比較でも前段の短縮は観測したが、端末OSの開始遅延と外れ値があり、全体の高速化は確定していない。

完全な1周期で真正性検査を16回行い、Sessionの検査64回・FDの確認128回を実行していることも独立計測した。検査1回の非profiled CPU時間は中央値24.167µs。開始前・終了後の段階検査へ集約する案の予想削減は約145µs/周期で、約450µsの収集側増加全体の説明にはならない。原票・真正性・取消の検査は現ソースで維持し、次の細かい最適化をこの数値から選ぶ。

Jetsonの共有接続が切れており、この新ソースのARM64ビルド・CPU比較・実CANはまだ実施していない。次は別配置のキットでARM64ビルドとCPU比較を行い、新ソースに結び付いた無出力5→501周期、ゼロゲイン、箱支持2→10秒を確認する。長時間の実出力と荷重支持は、その結果を別に記録する。
