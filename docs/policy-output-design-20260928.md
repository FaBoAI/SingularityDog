# 学習済みモデルの実出力試験：設定と証拠の分離

2026-09-28。これはオフラインで準備した実装設計です。この文書の作成・テストでは実機を駆動していません。

目標は、同じ短い試験のために校正や確認を最初から繰り返さず、検証済みの記録を再利用して学習モデルの目標値を実機へ送ることです。まず胴体の支持を残した、最大10秒の全12軸試験だけを扱います。支持台を抜く操作、自立、歩行はこのプロファイルの範囲に入りません。

## 同夜追加：現在姿勢から小さく動かす限定試験

明示選択のV3 `bounded_relative_supported_v1` は、絶対原点の精度を未知のまま記録し、現在姿勢からの相対変位を測る試験です。12軸の水準器原点・回転方向・新規角度記録・現物の各方向3°の経路確認を参照します。数値処理に使う2LSBの余裕を、水準器や機構の精度とは呼びません。

この方式では、生の学習目標をモデル範囲で確認し、現在姿勢へ混ぜた実送信目標を局所の現物範囲で確認します。変位は1°以内、実行3秒以下、混合率1%以下、Kp3・Kd0.15以下に限定します。9月28日夜の具体案は2秒・0.5%です。位置・速度・トルク・温度・鮮度・電圧監視と全軸STOPは維持します。

操作者のUSB切断試験省略指示は `command_loss_only_supported_trial` として別のハッシュ固定記録へ保存します。実際の全12軸指令途絶・無効化・終了STOP、個体とFWの一致を必要とし、USB切断は未試験のまま残します。絶対校正、動的速度・トルクの独立検証も完了と偽りません。箱支持を残し即時40V遮断を担当する人がいる限定試験であり、この設定・結果を支持台取り外しや歩行の承認に流用することはコードでも拒否します。以下の通常プロファイルの既定条件は変えません。

## 実装API

`runtime/singularitydog_hw/policy_live_profile.py` はファイルだけを読みます。SSH、CAN、I2C、torchのモデル読込みは行いません。

```python
from singularitydog_hw.policy_live_profile import load_profile, template

plan = template()  # 未解決事項とnullの校正/ゲイン/UID。実出力不可。
profile = load_profile('/private/path/profile.json', require_approved=True)
axis1 = profile['axes']['1']  # CAN ID順、文字列キー1..12
```

```bash
PYTHONPATH=runtime python3 -m singularitydog_hw.policy_live_profile \
  --write-template /private/path/profile.json
PYTHONPATH=runtime python3 -m singularitydog_hw.policy_live_profile \
  --check /private/path/profile.json --plan-only
```

`--plan-only` は未承認テンプレートの表示用です。承認済みファイルなら通常と同じ全検査を行います。`approved_for_supported_policy_output` をtrueに変えただけでは通りません。テンプレートにゲイン・原点・UIDを推測で埋めません。

返却値は独立したplain dictです。`axes[str(id)]` は次の値を持ちます。

| 項目 | 意味 |
|---|---|
| `uid`, `sign`, `offset_rad` | 校正ファイルと一致する個体・変換係数。`q_model = sign * raw + offset`。電源世代の360°分岐は実行側で別途結び付ける |
| `physical_lower_rad`, `physical_upper_rad` | 現物で確認したモデル座標の可動範囲。URDF範囲内に限定 |
| `uncertainty_rad` | 原点・姿勢合わせの不確かさ |
| `lower_rad`, `upper_rad` | ローダーが不確かさを内側へ差し引いた有効範囲。エンベロープへこの値を渡し、再度差し引かない |
| `kp`, `kd` | レビューされた試験ゲイン |
| `max_command_velocity_rad_s`, `max_command_acceleration_rad_s2` | 指令軌道の速度・加速度上限 |
| `max_tracking_error_rad`, `max_measured_velocity_rad_s` | 実測の追従差・速度監視 |
| `max_measured_torque_nm`, `max_estimated_pd_torque_nm` | 読取りトルクの監視と、指令前の推定PDトルク予算を別々に扱う |
| `max_temperature_c`, `max_displacement_from_start_rad` | 温度と開始姿勢からの移動範囲 |

ゲイン・トルク・温度の上限は、この短時間試験の実装範囲です。RS05や黄色い構造部材の保証限界ではありません。目標速度0・フィードフォワードトルク0でも、PD制御の合計トルクが0になるわけではありません。

## プロファイルに結び付けるファイル

`artifacts` の各値は `{ "path": "...", "sha256": "..." }`。相対パスはプロファイルの場所が基準です。次の6ファイルをすべて固定します。

1. `calibration`：既存 `MANUAL_NOMINAL_CANDIDATES_ONLY` スキーマ。12軸UID、符号、オフセットを照合。
2. `mount`：既存 `IMU_MOUNT_CANDIDATE_ONLY` スキーマ。右手系の回転行列を検査。
3. `bias`：既存 `GYRO_BIAS_CANDIDATE` スキーマ。独立したA/B記録を持つセンサ座標ジャイロ補正候補。
4. `model_manifest`：`native-policy-overnight-v1` の等価性検証済みファイル。実行側のローダーがABI、ライブラリ、モデル本体を再照合。
5. `pipeline_diagnostic`：取得・実推論・全12軸STOP送信を行った `native_pipeline_benchmark` のreport.json。
6. `hardware_review`：下記の現物確認をまとめた、明示的なレビュー記録。

既存の候補ファイルを「承認済み」に書き換えません。元の候補とその内容を確認したレビューを分け、どの結果を採用したか追跡します。`bundle_path` の3ファイルも既知の学習モデルのSHA256と照合します。

`profile['boot_id']`、`motor_power_epoch` は実行時の起動・40V電源世代です。再起動／電源再投入後の生角度を、前回の数値として扱いません。実行側は今回の12軸UIDとType17角度を取得し、個体一致と一意に決まる角度分岐を確認します。

## hardware_review の契約

これは測定データを自動承認するファイルではなく、測定を読んだ担当者の結論です。ファイルのハッシュとスキーマが合っても、現物の確認が正しかったことまではソフトで証明できません。

| キー | 必要な内容 |
|---|---|
| `schema`, `scope` | `singularitydog.supported-policy-hardware-review.v1` / `supported_characterization_only` |
| `review` | `reviewer`, タイムゾーン付き `reviewed_at`, `decision="APPROVED_SUPPORTED_CHARACTERIZATION"`, `rationale` |
| `assembly_id`, `uids_by_id` | 現在の組立識別子・12個のUID |
| `reviewed_settings_sha256` | `reviewed_settings_sha256(profile)` で得る値。ゲイン・限界値・原点・移動量・推論重みを含む。数値を変えると再レビューが必要 |
| `artifact_sha256` | `hardware_review` 自体を除く5入力のSHA256 |
| `source_captures` | 元の実機記録JSONへのpath/SHA256のリスト。相対パスはレビュー記録の場所が基準。内容を担当者が確認する |
| `angles[ID]` | 原点・符号、現物範囲と干渉、電源投入時分岐方法を確認した3つの真偽値と、プロファイルと同じsign/offset/範囲/不確かさ |
| `imu` | 固定取付方向、鼻上げ・左上げ・左旋回の方向、別の静止記録でジャイロ補正、重力方向を確認。重力方向最大誤差・残留ジャイロ・静止ノルム範囲と偏差の説明を記録 |
| `type2_dynamic[ID]` | 実際に動かした記録で出力軸角度、速度換算と符号、トルクの解釈を確認。固定範囲は位置±12.57rad、速度±50rad/s、トルク±5.5Nm |
| `device_watchdog[ID]` | 実際の指令途絶試験とUSB切断試験、途絶後に無効化した確認、設定200ms、最大実測停止時間、FW版数、motor_model=RS05 |
| `mode0_readback_required_before_enable` | true。過去の確認で代用せず、毎回有効化前にMode0を読み返す |
| `timing_budget_rationale` | 診断結果に対して採用する最大周期・連続超過数の理由 |

フィールドの正確な名前はモジュールの `_hardware()` が契約です。単体テストの合成レビューを実機のレビューとして使うことはできません。テストでは学習モデルの固定ハッシュ自体を明示的に差し替えてあり、製品設定では読み込めません。

静止時のType2/Type17比較は、位置の一致を見るのに役立ちますが、速度換算の動的妥当性は示しません。従来の角度差・静止時ノイズの記録だけでは `type2_dynamic` を承認しません。

IMUの約9%の静止ノルム差は、単一姿勢から加速度バイアス／スケールを推定して帳尻を合わせません。重力方向の複数姿勢照合と生ノルム範囲を確認し、正規化した重力方向をこの試験に使えるかを明示的に評価します。絶対yawは静止姿勢からは得られません。

## 20msと短い実出力の関係

実出力前に、同じモデル・校正・IMUで最低20周期の全工程無出力診断を確認します。読み取りだけの速度や合成入力の推論速度では代用しません。

目標周期は20ms固定です。支持台上の原因切り分けでは、レビューを付けて `hard_cycle_ms` を20〜60ms、`max_consecutive_20ms_misses` を0〜3にできます。テンプレートは20ms／0回です。周期超過を無視する設定や、無制限の待ちにはできません。入力の鮮度は最大周期以下です。別の制約である入力間隔 `max_sample_gap_ms` にはOSのスケジューリング差のため最大周期＋1msまでを許し、テンプレートは21msにします。この1msは入力の古さや処理時間に加える余裕ではありません。

20ms超過は、実処理時間または最古入力の取得開始から最終ホスト送信までの時間で数えます。スリープ復帰の微小な遅れをこの計算に混ぜず、復帰間隔は別に記録し1msの診断許容を設けます。開始間隔が極端に空いた記録や、重複周期、時刻の逆転は拒否します。要約の中央値を信用せず、元の単調時計タイムスタンプで再計算します。

ここで得られるのはSTOPを送った診断の実績です。実際のMIT指令に切り替えたときの20ms達成とは区別し、`actual_policy_output_20ms_verified` はfalseのままです。最初の実出力試験で同じ区間を改めて記録します。

## 通信断時の停止

USBが抜けた後、ホストからSTOPを送ってもモーターへ届きません。PythonのfinallyやC++の例外処理は、送信経路が残っているときの停止処理です。SSH切断・プロセス停止・ホスト電源断を、ホストのSTOPだけで保証しません。

このため、12台それぞれについて**設定値を読み返しただけでなく、指令が途絶したとき実際に無効化すること**が必要です。USB切断でも別プロセスの送信が続いていないことを確認します。自動報告だけでタイムアウトが更新される実装なら、想定したwatchdogになっていないので採用できません。実装は従来と同じ4000tick＝200msに固定し、別の値で行った試験を証拠として流用しません。

watchdogは無効化までの最大移動量や、脱力後の機体支持を保証しません。最初の実出力試験では支持を外さず、即時40V遮断の担当と経路を維持します。身体での支持だけに依存した状態でソフト開発の待ち時間を作りません。

## 効率化する実行順序

1. オフラインでプロファイル・モデル・証拠の全照合を済ませる。パス違い／不足フラグはこの段階で解消する。
2. 実機で一度だけ支持・接触なし・即時Offを確認し、12台を一括で新しい起動／電源世代へ結び付ける。
3. 同じ実行プロセスでモード・watchdogの読返し、初期入力の範囲を確認する。
4. 日本語の開始音声後、現在位置からゲインを滑らかに上げ、モデル出力の重みを増やす。各軸の速度・加速度・開始位置からの変位を制限する。
5. 正常終了は、加速度制約で減速する時間とゲインを下げる時間をあらかじめ最大10秒内へ予約する。硬い異常条件では通常の滑らかな停止より即停止を優先する。
6. 最後のSTOP返信と実物の様子をまとめて確認し、成功した軸・項目を再試験の対象から除く。

これで毎回の確認の重複を減らせます。現在の未解決条件を削除して成功扱いにする効率化は行いません。
