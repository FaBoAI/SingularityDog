## 20msの設計予算と優先対策

以前の境界確認条件では、取得中央値9.879ms、入力組立て3.587ms、入力検査・推論・変換9.369ms、代理送信区間7.768ms、全工程31.759ms（最大33.226ms）だった。取消・期限・受信の対応検査は各操作で維持し、起動IDだけを明示した境界でfreshに読む条件である。warmup10→260回のCPU単独比較は初回中央値3.595→3.267msで、統合時のモデル呼出し約6.9msとの差の原因はまだ確定していない。

CPU governorを既存の周波数上下限内で`performance`へ切り替えた別試行は、入力STOPのID4・10への返信が欠けて中断した。3回予定のうち1回だけで、推論と後段送信には進んでいない。親処理・独立watchdog・外部読取りで元の`schedutil`設定への復元を確認した。全12台の通常読取りも再確認済みである。この中断した試行から全工程の改善値は得られていない。

[比較ツールの準備・検証記録](hardware-pacing-optimization-20260925.md)。再接続後、0.8ms・未返信3件で通信単独の全12台取得は中央値8.720ms／最大8.729ms（3回、欠測なし）。0.5msは返信欠落で中断した。その後の実入力統合比較も3回完了し、全工程中央値24.568ms／最大25.037msとなった。CPU条件と通信条件が変わっているため、短縮を一要因だけへ帰属しない。

同時未返信件数2／3／4と送信後の最小間隔0.5／0.8／1.0msの有限比較は完了し、次の統合条件に3件／0.8msを選んだ。欠けた4台目の送信直前には既に最初の返信を受けており、未返信件数は2件だったため、window=4だけを原因とは断定しない。設定間隔を守っていても基板側が処理できるとは限らず、欠測を無視して速度だけを合格にしない。

姿勢保持が難しい間に実施した保存入力のobserver比較では、診断データを減らす候補が中央値6.231ms→5.957ms、最大7.000ms→6.777ms（各40回）。出力・内部状態・12種の異常入力の拒否は一致した。その後、この軽量候補・所有権の一回引渡し・0.6ms間隔を組み合わせた実入力試験を3回完了した。全工程は中央値22.283ms、最大23.193msで、中央値約2.3ms、最大約3.2msの不足が残る。複数の条件を変更したため、短縮をモデル単独へ帰属しない。モデル呼出し自体は3.730／5.993／5.303msと変動した。保存した今回の実入力で、姿勢・初回呼出し・CPU競合の影響を切り分ける。

今回の3入力を保存して計66回の単独再生も行い、元モデル／leanの全出力・内部状態は一致した。leanの初回モデル呼出しは3.066〜3.440msで、統合時の最大5.993msは再現しなかった。その後、統合と同じperformance条件で180回の待機スレッド比較を実施したが、2msポーリング→期限付き通知待機の中央値差は約0.002msで、有効な短縮は確認できなかった。

入力組立ての重複コピー削減は保存入力90組で中央値1.320→1.264ms（約0.056ms短縮）。別の72回比較では、100ms待機後のobserver中央値4.138msが再warmup後3.856msになった。いずれも全出力・内部状態の一致を確認したが、実機の数msの遅延はまだ十分に再現していない。その後、既存10回warmupを機器準備の後・新しい入力取得の前へ移した統合比較を3回完了。入力検査・実推論・結果変換は中央値4.492ms、モデル呼出し単独は3.255～3.515msとなった。全工程は中央値21.234ms・最大21.865msで、次は取得と送信に残る待ちを分析する。保存入力の時間を全工程から単純に引かない。

**取得5ms＋入力組立て・推論8ms＋送信4ms＋余裕3ms＝20ms**を設計予算とする。各値は未達・未測定の目標配分で、現在のCH340構成で達成できるという予測ではない。

**20ms周期と、最古入力から出力まで20ms以内は別条件である。** 10ms間隔の報告をキャッシュしても入力年齢は0にならない。受信時刻と取得開始時刻を保持し、入力の古さ、軸間の時刻差、内部サンプル時刻が不明な範囲を記録する。古い入力の再利用や未返信のまま先へ進むことで達成扱いにはしない。

## 通信修正の到達点

起動確認を所有FD＋fresh `pread`へ共通化した過去の個別STOP比較では、38.281ms→30.223msを各1回観測した。[r7記録](hardware-stop-guard-20260925.md)。これは今回の全工程に同じ短縮幅を足せる根拠ではない。

FW更新後、単台の約100Hz報告と解除は初回・修正版で各1回、3台は初回1回成功した。前6台は初回にID3・4、修正版にID6の開始応答・報告が欠け、いずれも計測開始前に失敗した。初回は解析停止時の15バイト残留を古いまま判断したため、解除後の最終STOPも送信前に拒否された。

修正版は報告区間の全生バイトを別パーサーで一度ずつ再解析する。実機08で2,975バイト／175フレーム、破棄0・末尾残留0、100ms静穏、全6台の最終STOP返信まで確認できた。開始失敗はそのまま保持している。解除成功1回を6台運用の安定性とは扱わず、後6台・前後12台へはまだ拡大していない。全12台の最終確認はFW0.5.0.13、識別一致、STOP mode0／fault0、静穏、ポート閉鎖・排他解放で完了した。

送信・受信の期限、取消、送信直前の所有権とポート確認は維持する。重複検査を整理する際も、抜差しや再起動検知をキャッシュで省略しない。読取り直後に異常となったバイトも保存し、「受信なし」と「受信したが採用不可」を区別する。

## CPU側で先に進めること

コピー単独の保存データ比較は、内容と元の時刻が一致し、中央値約0.250ms→0.134msとなった。ただし最大は0.277ms以下→1.740msへ悪化した例もある。[CPU単独比較](hardware-post-firmware-remediation-20260925.md#cpuコピー単独比較)。今回の統合比較でも全工程は改善していないため、中央値だけで採用しない。

1. 同じモデル・同じ入力系列・同じ内部状態の初期化で、モデル本体と入力準備の費用を分離する。
2. 不変レコードと有界バッファで所有権を明確化し、不要なコピー・診断整形・テンソル生成を周期外へ移す。新しい入力、時刻、故障、範囲との対応は維持する。
3. 出力とモデル内部状態を全件照合する。単独試験の短縮値を統合時の短縮量として流用しない。
4. 通信・IMU担当とのCPU競合を測り、スレッド設定や担当分離を一要因ずつ比較する。

warmup、`inference_mode`、推論スレッド数1は既に適用済みで、新しい改善策には数えない。以前の1バス分のフレーム解析・値変換は合計約0.06msだったため、パーサーだけのC++化を最優先にはしない。

## 通信機器の切り分けと次の判定

CAN 1MbpsとUART 921600bpsは別設定である。現在のホスト測定はCAN線の速度・完了時刻を保証しないため、UARTや無関係な`can0`を推測変更しない。受動観測で送出と応答を分け、それでも欠測や通信待ちが支配的なら、現在のCH340経由とLinux対応SocketCAN機器を同条件比較する。29ビット拡張ID、1Mbps、前後2バス、受信時刻、エラーフレーム、bus-off通知を確認する。[Linux公式SocketCAN資料](https://docs.kernel.org/networking/can.html)

別機器の採用だけで20msは保証されない。同じモーター・FW・配線・要求で比較し、同型USB基板の増設より先に待ちと欠測の箇所を明らかにする。

次はオフライン同値検証→有限の停止中通信比較→入力・実推論・STOP代理の統合比較→10秒／60秒の有限連続測定の順に進める。中央値だけでなく最大・p95／p99・欠測・期限超過・入力年齢を記録する。STOP代理と駆動中Type1の往復は別に検証し、実出力は投入条件が揃ってから支持下で開始する。
