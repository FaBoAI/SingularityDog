# ロボット実装の30Hz対応 — 2026年10月13〜14日

30Hzモデルを使うロボット実装を追加し、全軸のhost書込み20msと返信33.33msをC++で分離した。Jetsonの無出力5→501→501周期に続き、箱を残したゼロゲイン2秒・54周期と、学習目標0.5%・最大1°・Kp3/Kd0.15の実出力2秒・58周期を正常終了した。実出力の取得→推論→全軸書込みは最大17.667111ms、周期開始→最終返信は最大21.078828msで、20msの送信期限と33.33msの返信期限を全周期で満たした。全12軸のSTOP、設定復元、音声・現物異常なしを確認した。次は別ソースでの人支持による短い荷重試験を準備する。

[10月14日の追加原因調査](type1-command-gap-investigation-20261014.md)では、Jetsonの仮想4系統でC++復帰時のGIL再取得経路に最大1.079msの遅延を直接確認した。1系統の対照は最大10µs。診断修正版は44件合格・skipゼロ。過去の実機停止を成功へ変更せず、通信開始前の遅れとC++での受け渡し統合を分けて進める。

従来の50Hz設定は既定として残し、新しい30Hzモデルを明示したときだけ別の契約・記録形式を使う。旧actorを遅い周期で呼ぶ変更ではなく、再学習済みactorと30Hzの状態付きcontrollerを一緒に読み込む。[再学習と有限評価](training-30hz-20261013.md)も参照する。

詳しい時間記録を選んだ再測定は、入力の間隔33.340489msに対し指令計算の間隔34.868540msだった。取得・IMU待ち・推論と、指令計算が終わる位相の変動を別々に調べる。両回の原返信に欠落はなく、停止した周期の学習目標は未送信。完了済み88／175周期の入力→全書込みは最大18.221699／17.769960msだったが、10秒完走へ読み替えない。

原因調査後の箱支持再試験では、追加診断ありの2秒が初周期で停止し、前回成功時と同じ追加診断なしの2秒も31周期で指令計算間隔34.521432msの上限超過により停止した。完了31周期の入力→全軸書込みは最大17.672679ms、全1,100要求に返信あり、全12軸STOP・復元・現物異常なしを確認。10秒再試験は未実施。[再試験と初期診断の修正](type1-command-gap-investigation-20261014.md#原因調査後の箱支持再試験)。

## 時間の扱い

| 対象 | 上限・周期 | 意味 |
|---|---|---|
| 推論モデルの更新周期 | 正確な1/30秒 | 状態、filter、歩容位相も30Hz用controllerが進める |
| 推論へ渡す入力の鮮度 | 20ms | 古い取得値を33msの入力として再利用しない |
| 周期開始・最古入力→全軸host write | 20ms | 両方を満たす早い方の期限。全12軸のwriteを記録する |
| Type1全返信 | 実開始＋33,333,334ns | 20ms送信期限と別に確認する。CAN上でモーターが受け取った時刻の証明ではない |
| 直前返信の連続性確認 | 最大34,333,334ns | 次の保持処理へつなぐ履歴の上限。新しい推論入力の鮮度ではない |
| host watchdog | 40ms | 既存値を維持 |
| モーター通信断保護 | 200ms | 初期設定と読戻し、終了STOPの確認を維持 |

未返信、送信期限超過、古い入力、異常値は成功へ読み替えない。返信完了後の確認処理だけに、既存方式の有限な許容枠を別に記録する。停止要求は従来どおり各CAN所有者から繰り返し送り、返信の曖昧性は後続の正常返信で消さない。

無出力診断は30Hzの取得・モデル・周期を確認する。最初の配置版R2はSTOP代理の返信期限も20msのままであり、下記の初回中止が発生した。修正版R3は30Hzを明示した経路だけ、STOP代理の全host書込み20msと返信最大33.33msをC++でも分離する。既存50Hzの20ms契約は残す。これだけで実Type1の返信経路を合格にせず、旧20msの成功原票へ30Hzというラベルを付け直さない。

## 新モデルの位置付け

モデルは500更新で作成し、CPUでの一致検証を通した評価候補である。GPUの有限評価は7ケース中5ケースが12秒完走した。左移動は112step・約3.733秒、停止保持は97step・約3.233秒で`terminated=true`となった。終了理由の個別内訳は未記録であり、転倒・接触・速度のどれかとは断定できない。

完走した5ケースも歩行の最終合格ではない。モデル原票、ローダー、無出力診断には歩行許可を持たせない。未計測の負荷履歴入力も、計測値ではなく明示した仮説として残す。

## Jetson起動後の順序

1. 新ソースとモデルを配置し、SHA、Linuxビルド、CPU推論、controllerの30Hzとresetを照合する。[成功設定](jetson-best20-settings.md)と[設定の証拠](../evidence/jetson-best20-settings.json)を毎回参照する。
2. 現在の起動・40V電源区間・4系統の配線・全12軸識別・角度・35〜42Vを読み直す。保存済みの姿勢や承認を現在の状態へ自動転用しない。
3. 900µs送信間隔・window3で無出力5→501周期を実測する。新モデル・新ソース・30Hzの原票、全返信、終了STOP、設定復元を保存する。
4. 箱を残す現在条件を結び、ゼロゲインの通信断保護とType1返信を確認する。
5. 同じ契約で、箱支持の最大1°・学習目標0.5%の2→10→20秒を段階的に実施する。20ms以内の全軸host write、33.33ms以内の返信、追従、全12軸STOPと実物の結果を別々に確認する。

性能設定はmain CPU4、4CAN所有者をCPU0〜3、IMUをCPU0〜3、nice −10、数値演算1thread、Python switch100µs、timer slack1000ns、release spin500µs、warmup10＋pin後10とresetを参照する。CPU周波数・C7・EMCの一時設定と終了時の復元も実機で読む。900µs／window3は比較基準であり、新30Hzの実測合格を意味しない。

支持付きの試験が終わってから、別の荷重支持・自立・低速歩行の条件を準備する。今回のキットは箱撤去や歩行へ自動で移行しない。

## 現起動での12軸読取り

ユーザーが40V On・箱で胴体支持・QDD脱力・手離し・即時Off可能と回答した後、Type0／Type17だけで132要求を送った。48回のポート別識別探索と、既知の12個体・3軸ずつの配線の一致を確認してから、84回の識別再確認・モード・電流・電圧・位置読取りを行った。想定した36回の「そのポートに対象IDがいない」探索と、実在する軸の返信欠落は区別する。

全12軸を読め、起動とデバイスの対応は収録中に変わらなかった。位置3点の最大幅は0.016993511°で、読取りの静止幅0.1°以内。モード値は全軸0、電流値は全軸0Aだったが、これをSTOPや無励磁の独立した証明にはしない。有効化・Type1・STOP・パラメーター書込み・学習目標は送っていない。

電圧は30.106533〜31.124119Vで、全12軸が下限35V未満だった。読取り原票は成功として保存し、電圧条件は不合格として分ける。充電・交換後の新しい電源区間を記録し、識別・角度・電圧を再確認してから30Hzの無出力5→501周期へ進む。低電圧の原票を編集して計測条件を満たしたことにはしない。

別担当が132要求と96返信を原バイトから検算し、復号値・時刻・識別・集計に重大な矛盾がないことを確認した。保存済みの対応する原点・符号を使った角度だけの解析では、全12軸で2πの枝が数値上ひとつに決まった。これは絶対原点精度や現物の可動余裕の証明ではない。

次の30Hz計測に向け、配置済み全992ファイル、旧profileの数値・IMU参照、新モデルとARMライブラリを結ぶ入力を固定した。デバイスを開かないPLAN検査は、今回の35V未満の原票を正しく拒否した。入力の準備完了と計画の合格は分けて残す。充電・交換後の新しい読取り原票でPLANを通してから、STOP代理だけの5→501周期を実測する。

## 充電後の初回計測と返信期限の修正

充電後の最初の2回はID3が42.001770Vで上限42Vをわずかに超え、時間計測へ進まなかった。上限は変更せず、CPU計測後の新しい原票で全軸40.492935〜41.931591Vを確認し、PLAN合格後に900µs・window3・成功時のCPU設定で無出力5周期を実行した。

原通信には各ポートで先頭の返信17byteと2軸目の15byteまでが残り、終了STOP側に残りの2byteと3軸目の返信17byteが混ざっていた。別担当も原バイトから対応ID・mode・faultを検算した。永久的な返信欠落とは断定せず、期限で受信途中を切ったことと終了STOPの取引曖昧性を分けて保存する。後から返信を再構成できても、失敗周期や終了STOPを合格へ読み替えない。

修正は送信20msを維持し、30HzのSTOP代理返信だけを実開始＋33,333,334nsへ分離する。C++で全writeの直前・直後を20ms期限と照合し、返信には別の期限を渡す。未送信・未返信・fault・STOP曖昧性・入力鮮度20msは維持する。新しいソース・ライブラリで模擬通信を検証し、別のキットとして配置してから5→501周期を取り直す。

新モデルの単体CPU計測は501回（初回1＋定常500）、合成入力、warmup10＋10後のreset、数値演算1thread、main CPU4で実施した。定常中央値5.548334ms、最大5.676786ms、初回5.653842ms。CPU・C7・EMC・main設定の復元を確認した。CAN取得・observer全処理・送信・実30Hz周期を含まないため、20ms全ループの合格には数えない。

ユーザーは30ms送信の比較も候補として許容した。現在の送信17.342451msは20ms以内なので、まず20ms送信＋33.33ms返信を検証する。30ms送信を選ぶ場合は、同じ30Hz周期で返信余裕が約3.33msとなる別条件として原票に残し、自動的に既定へ変更しない。
