# 25 ms 周期案の判定 — 2026-09-29

支持台を残した学習目標の短時間出力では、直近の r7 は開始段階の第3・4周期がそれぞれ 20.162252 ms、20.170701 ms となり、連続超過の設定で停止した。全12軸の STOP 返信と停止後の mode 0 を確認したが、学習目標はまだ送っていない。原レポート SHA-256 は `bb8cd4e901f67a760b0854f0208a5f77b22a6fa1158db18cd96607784befa00f`。原レポートは非公開保管し、UID・生角度・シリアルの記録をリポジトリへ含めない。

保存した5周期の全工程最大は 20.170701 ms、周期開始から最後の返信までの最大は 19.497719 ms。単に上限を25 msと比較すると全工程超過は0件で、観測最大値に対して約4.83 msの余裕がある。これは**20 msで取得した記録に別の閾値を当てた結果**であり、25 ms周期の実測でも、40 Hzの学習済み実出力の承認でもない。比較用の読取り専用ツールは [`replay_25ms_feasibility.py`](../tools/replay_25ms_feasibility.py)。

25 msを現行の実出力へそのまま設定すると、次の整合が崩れる。

| 項目 | 現行 | 25 ms案で必要な作業 |
|---|---|---|
| 学習モデル | 学習契約とSwingCoreの内部刻みが20 ms | 40 Hzで位相・フィルター・行動履歴・歩容をシミュレーションで再評価する。内部刻みだけの変更は同値ではない |
| 設定・実行周期 | プロファイルとランナーは20 ms固定 | 40 Hz専用の設定、起床・期限・停止判定を別途設計する |
| 入力・指令間隔 | 入力鮮度20 ms、連続間隔21 ms以下 | 25 msごとの取得では間隔上限を必ず超える。検出遅延を含めて新しい上限を審査する |
| 全軸電圧 | 各バス1軸を6周期で巡回、キャッシュ期限126 ms | 6×25=150 msで期限切れ。巡回頻度を上げ、追加要求込みで再測定する |
| 監視・停止 | ホスト監視40 ms、QDD指令断監視200 ms | 新しい周期との関係、両バスSTOPの故障注入と実測をやり直す |

現行モデルの実出力は20 ms目標を維持し、返信後の処理と受信デコードの費用を縮める。今回の約0.17 msの超過を削れるか、支持台を残して実測する。短時間の超過を許す場合も、最終ホスト送信・全返信・入力鮮度・可動域・故障・STOPの制約を緩めず、周期開始間隔を別に報告する。保存記録に対する25 ms比較が成功しても、これらの実測を代替しない。

40 Hzを別候補として進める場合は、25 msモデル評価、電圧巡回の再設計、無駆動の実入力→推論→STOP計測、支持下の故障注入・有限時間実出力の順で検証する。支持台を外す試験は独立した落下受けまたは補助者を用意してから行う。
