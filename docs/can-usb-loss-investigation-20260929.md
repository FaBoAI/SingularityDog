# CAN/USB返信欠落と1周期skipの調査 — 2026-09-29

**短い遅着で救える可能性のある例と、返信全体が届かない例が混在している。USB／変換基板／CAN／QDDのどこで失われたかは、まだ確定していない。** 実機は各試験後、操作者が箱支持と現物異常なしを確認した。以下では無駆動読取り、脱力中ゼロゲイン、実出力を区別する。

r3の末尾2バイトは停止処理中の集約された受信証跡にある。個別到着時刻がないため、**追加20msで必ず救えたとは判定しない**。r3ではID8も未解決であり、ID12の再構成だけで試験全体を継続可能にしない。

正常なType1返信はおおむね1.6〜2.8msで受信し、複数フレームを同じreadで取得している。USBシリアルのreadがフレーム単位でないこと自体は異常ではない。現C++実装は分割・連結受信を処理する。host write成功だけでは変換基板への到着やCAN送信成功は分からない。試験が最初の欠落で終了するため、これらの標本から長時間の独立した欠落確率を推定しない。

全軸のmode0返信を後から受信していても、先行Type1が未完了の軸はSTOPの返信との識別が曖昧になる。**STOP送信失敗、STOP応答未観測、先行返信との対応不明を区別する。** 待機を1秒へ延ばすだけでは、この識別問題は消えない。[STOP再送の実装](stop-retry-20260929.md)

### 追加実機試験：Type17読取りとUSB双方向記録

箱で胴体を支持し、4足接地・QDD脱力・40V即時Offを操作者が確認した。同一起動`274a4717-d613-489e-b5bf-48ee50690111`で、0.8ms間隔・前後各window3の無指令Type17読取りを500周期実施し、全周期完了した。角度/IMU取得中央値12.725ms、最大13.506ms、取得から周期終了まで中央値14.046ms、最大14.895ms。**これは推論・Type1目標・STOP返信を含む20ms試験ではない。** 操作者は現物異常なし、箱・40V状態不変と回答した。

最初のxHCI記録器はCH341の受信pipeを誤って組み立て、送信側しか捕捉していなかった。実機の全bulk転送探索では、送信pipeが前`3221292288`・後`3221292032`、受信pipeが前`3225486720`・後`3225486464`と判明した。CH341ドライバーが受信pipeへエンドポイントアドレス`0x82`全体を渡すため、受信pipeには通常の方向ビットに加えてbit22も立つ。記録器と単体検査を修正した。探索記録自体はバッファ上書きがあったため件数の証拠には使わない。

修正版はCH341の前後送受信pipeだけを記録し、CPU別overrun/droppedが全て0で完走した。各アダプターについて、OUT投入/完了は各6006件、IN投入/完了は各3508件。IN実データは各3000件×32バイト＋500件×12バイト＋起動時6件×17バイトで、500周期×12返信＋起動時6返信に対応する。停止時の0バイトINは各2件。USBホスト側ではこの試験中に未完了URBを観測していない。これはType17の正常例であり、過去のType1欠落箇所を特定したものではない。

`xhci_urb_giveback`の`status != 0`フィルターは正常に完了した転送も全件拾ったため、USBエラー数として扱えない。記録器はその二重収集をやめ、バッファを増やし、overrunがあれば不完全とする。URBの投入からIN完了までの時間には、QDD/CANからの返信待ちも含まれるため、USB自体の遅延として引用しない。

STOP返信込みの無駆動試験も試みたが、1回目はTorchのないPython環境で通信前に中止、2回目は現在姿勢が保存済みモデル関節範囲外となり**0周期で中止**した。有効化・学習目標送信はどちらも0。初回の200周期試験は取得専用フラグを使っておりSTOP返信を含まないため、STOP試験の成功数に算入しない。現姿勢の再照合なしに範囲を広げない。

停止した軸は右後付け根ID9で、旧校正の生角約−0.673radから現読値約＋5.633radへ約＋6.306rad変わった。旧オフセットのままではモデル角約＋6.279radとなり、登録範囲±0.5radを超える。操作者は電源再投入後も実物を一回転させていないと確認した。現起動の無出力読取りと診断用プロファイルを照合するとID9のモデル角は−0.0043radで、12軸すべてが登録範囲内に入った。この監査でID9に追加した整数回転は0であり、既存プロファイルのオフセットが現読値を範囲内へ写像している。旧候補とのオフセット差の由来と現物の原点・正方向・電源epochの承認が済むまで、この診断値を実出力補正へ採用しない。他11軸では同じ約2π差は見られなかった。

## skipの試作仕様

1. 全要求を書き終えた通常周期のみ対象。起動時・部分write・故障返信・切断・不正フレームは停止。
2. 20msを超えたら**目標更新をskip**し、推論も新しいType1送信も行わず、元の未完了要求の返信だけを待つ。再送しない。
3. 追加は最大1周期、仮の上限は周期開始から40ms。直前99周期にskipがあれば次のskipを認めない。
4. 返信が揃っても古い入力で再推論せず、`RESAMPLE_REQUIRED`を返す。新しい全軸・IMU・電圧の検証と継続可能な残り時間が必要。
5. 揃わなければSTOP。セッションのpoison・曖昧な返信状態を消して再開しない。

この40msは**オフライン仮説の上限**。現在のhost watchdog 40ms、sample gap 21ms、sample age 20msとはそのまま両立しない。実出力へ接続する際は、各軸の最終送信時刻から残る時間、再取得・推論・出力の所要時間を含めて上限を切り詰め、モデルの履歴更新も実際の時間経過に対応させる。40msの待機を現行プロファイルへ単純代入しない。skip周期を20ms成功件数へ混ぜない。

検証：Macの解析・状態遷移・実C++ socket通信・USB pipe検査は計74件成功。うち実C++の遅着25ms／末尾2バイト遅着／40msまで無返信の3ケースは、Jetson上でもsocket通信で成功。実機モーターの受信遅着を回復した結果ではない。

### 原因の絞込みと次の修正

実出力r7と同じSHAのC++ソースを監査した。受信した全バイトは計数され、不正・重複・不一致フレームはエラーとなるため、完全なID4返信を読み込んで黙って捨てた処理は見つからなかった。バスごとの単一所有者と、キャンセル後に同じ所有者でSTOPする構造にも競合の証拠はなかった。r7のSTOPは3回とも各102B・6返信で、遅れたType1に相当する余剰フレームはない。後続mode0を先行Type1かSTOPかへ断定できないため、単純な待ち時間延長で解決済みとはしない。

次の診断は実出力と同じ`native.ActiveSession`を使い、Kp/Kdの上限を通信器内部でも0に固定する。26要求・有効化状態を維持し、0.8ms/window3を基準に0.8ms/window2、1.0ms/window3を一条件ずつ比較する。周期の20ms目標と診断専用25ms返信期限は別に記録し、この猶予を実出力へ移さない。全12軸STOPとUSB記録を各試験に対応付け、500周期版を実行する場合も長時間実出力の合格とは区別する。

通信量26→14要求への削減は、現行の20ms鮮度条件ではそのまま採用できない。r7の隣接41周期では、前周期の最古出力要求から次周期の最終writeまで最短23.640ms、最終返信まで最短26.495msだった。前周期の返信を使うなら元の要求時刻を保持する必要があり、受信時刻や再利用時刻への付け替えでは解決しない。今回は通信量削減より、同じC++経路で送信密度と未返信数を切り分ける。

診断ログは直近イベントの上限付き保存に加え、全送信数・受理RXバイト・拒否RXバイトを別々に数えるよう修正した。長い計測でログ件数上限が先に終了条件になることと、拒否データが総受信量から抜けることを防ぐ。関連30件のオフライン試験が成功した。

別途、`policy_output_runtime.py`の電圧パイプラインを使わない経路で、ワーカー投入前に計算した相対時間が実行開始時に再起算される問題を修正した。取得・電圧とも同じ周期の絶対締切`hard_end`を渡し、キュー待ちで期限を使い切ったら送信前に停止する。関連124件が成功した。初回は既存の実時間依存テスト1件が電圧鮮度超過で失敗したが、単体と同じ124件の再実行は成功し、条件は緩和していない。r7は電圧パイプラインありの絶対締切経路だったため、これをID4欠落の原因とはしない。

この周期の直前まで、前USB INの累積量とアプリ受信量はともに5,202Bだった。欠落周期の3つのIN完了から対応するアプリreadまでは22.475／25.452／22.123µs。**ホストUSBに届いた完全返信をアプリが黙って捨てた、という説明を支持する証拠はない。欠けた17BはxHCIのIN完了記録にもない。** 一方、OUT完了は変換器内のUART転送やCAN送信完了を保証しない。USB payloadは収集しておらず、変換器／UART、CAN、QDD、USB受信境界のどこで欠けたかは、このメタデータだけでは確定できない。r7と同一の物理原因だともまだ断定しない。

後バスは19周期目の13要求221Bを全て受信した。試験全体の前バスは330要求・OUT 5,610Bに対しIN 5,593Bで、アプリ受信も5,593B。後バスは325要求・OUT／IN／アプリ受信が各5,525Bだった。前だけの17B不足は終了STOPを含めても一致する。xHCIは2,266イベント、前OUT投入／完了330件・IN投入／完了241件、後OUT325件・IN235件。各INには終了取消0Bが2件含まれる。計測は最初のアプリ送信より16.116秒前〜最終STOP返信より11.357秒後を覆い、全CPUのoverrun／droppedは0だった。

#### STOPの未確認理由と返信遅延を分ける

前バスのSTOPは3試行とも6軸分102Bを受信し、全返信がmode0・故障0、断片・余剰フレームは0だった。後バスも1試行で6軸分を確認した。**前ID6のSTOP未確認は、STOP中に返信が届かなかったという意味ではない。先行Type1の返信が未解決で、取引番号のない後続Type2をSTOPへ一意に帰属できないためである。** 後続mode0を先行Type1の回収済み証拠へ置き換えない。

初回STOPのUSB OUT完了からIN完了までの時間は前23.994〜26.388ms・後22.158〜24.722msで、遅延はxHCI受信時刻にも現れていた。IN完了後のアプリ受信までの差は前0.026〜0.194ms・後0.037〜0.210msだった。前の2・3回目STOPはUSB上で約2.6〜2.8msへ戻った。この初回STOPの遅延と、STOP以前から欠けているID6のType1返信は別に扱う。STOPを長く待つだけ、または返信欠落をskipするだけで解決したとはしない。

次の比較候補は、同じゼロゲイン・C++通信器で1.0ms/window3を短い5周期から確認し、全返信・STOP・現物結果を判定して50周期へ延ばすこと。送信間隔の変更効果と20ms所要時間を別々に評価し、25ms診断猶予を実出力へ転用しない。r23の50周期成功だけで通信安定性を判断できなかったため、欠落の再現とUSB側の不足量を引き続き一緒に記録する。[r23・r24の数値と原本ハッシュ](../evidence/can-usb-loss-followup-20260929.json)

### r29：再起動後に原本を回収し、速度監視停止を確認

同じ0.9ms/window3のr29は18周期を完了し、19周期目の出力返信検査で前ID6の速度読値が**0.6279087510rad/s**となり、0.5rad/sの監視で停止した。返信はmode2・故障0・32°Cで、開始中心角からの差は＋0.703338807°と3°の診断範囲内だった。停止理由は速度読値の超過であり、角度範囲超過・返信欠落・期限超過ではない。19周期目も前後各13要求、計26要求の返信を全て受信した。最後の完全返信は周期開始後18.506601ms、停止判定後の周期終了は19.379546ms。試みた19周期は全て20ms以内、中央値18.761262ms・最大19.379546msだったが、500周期の完走には達していない。

初期確認・STOPを含む全650要求に完全返信があり、前後各325要求・5,525Bの送受信が一致した。周期中だけでも各バス247返信を確認した。xHCIは2,244イベント、各OUT投入／完了325件、IN投入／完了235件（実データ233件＋終了取消2件）。INは各49件×17B＋138件×32B＋46件×6B＝5,525Bでアプリ受信量と一致し、記録窓は最初のアプリ送信より15.407秒前〜最終STOP返信より12.101秒後までを覆う。全CPUのoverrun／dropped、アプリの拒否・未解析バイトは0。全12軸STOPを各バス1回で確認した。
