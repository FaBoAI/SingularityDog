# CAN/USB返信欠落と1周期skipの調査 — 2026-09-29

**短い遅着で救える可能性のある例と、返信全体が届かない例が混在している。USB／変換基板／CAN／QDDのどこで失われたかは、まだ確定していない。** 実機は操作者が40V Off・箱支持・現物異常なしを確認済み。今回の追加作業では有効化・目標角・STOPを含むモーター指令を送っていない。

r3の末尾2バイトは停止処理中の集約された受信証跡にある。個別到着時刻がないため、**追加20msで必ず救えたとは判定しない**。r3ではID8も未解決であり、ID12の再構成だけで試験全体を継続可能にしない。

正常なType1返信はおおむね1.6〜2.8msで受信し、複数フレームを同じreadで取得している。USBシリアルのreadがフレーム単位でないこと自体は異常ではない。現C++実装は分割・連結受信を処理する。host write成功だけでは変換基板への到着やCAN送信成功は分からない。試験が最初の欠落で終了するため、これらの標本から長時間の独立した欠落確率を推定しない。

全軸のmode0返信を後から受信していても、先行Type1が未完了の軸はSTOPの返信との識別が曖昧になる。**STOP送信失敗、STOP応答未観測、先行返信との対応不明を区別する。** 待機を1秒へ延ばすだけでは、この識別問題は消えない。[STOP再送の実装](stop-retry-20260929.md)

## ホスト・USBの確認

- Linux 6.8.12-1021-tegra。前後のCH341は同じ480Mbpsハブの下で12Mbps接続。両アダプターのruntime powerは`on`／`active`。
- 読み出したカーネルログに試験中のUSB切断・リセットは見つからなかった。これだけで転送欠損や電気的な問題は否定できない。
- CH341モジュールSHA-256は`27c8f86b7fe0316bd56bb6161ac8e10dd3e0ae65b135b60bf71960bc345e23dc`。以前標準ソースと照合したビルドと同一。[ドライバー照合記録](usb-latency-settings-20260925.md)
- 現カーネルは`CONFIG_USB_MON`・`CONFIG_KPROBES`が無効。今回はカーネル／ドライバーの交換をしていない。
- 代わりに`xhci_urb_enqueue`／`xhci_urb_giveback`／`xhci_urb_dequeue`のtracepointが利用可能。実機のイベント形式を読んで確認した。

usbmonはホスト側の転送要求を観測する機能で、CANバス上の送信完了の証明ではない。今回採用したxHCIイベントもホスト側の証跡である。[Linux usbmon資料](https://docs.kernel.org/usb/usbmon.html)、[v6.8 xHCIイベント定義](https://github.com/torvalds/linux/blob/v6.8/drivers/usb/host/xhci-trace.h)

### 追加実機試験：Type17読取りとUSB双方向記録

箱で胴体を支持し、4足接地・QDD脱力・40V即時Offを操作者が確認した。同一起動`274a4717-d613-489e-b5bf-48ee50690111`で、0.8ms間隔・前後各window3の無指令Type17読取りを500周期実施し、全周期完了した。角度/IMU取得中央値12.725ms、最大13.506ms、取得から周期終了まで中央値14.046ms、最大14.895ms。**これは推論・Type1目標・STOP返信を含む20ms試験ではない。** 操作者は現物異常なし、箱・40V状態不変と回答した。

最初のxHCI記録器はCH341の受信pipeを誤って組み立て、送信側しか捕捉していなかった。実機の全bulk転送探索では、送信pipeが前`3221292288`・後`3221292032`、受信pipeが前`3225486720`・後`3225486464`と判明した。CH341ドライバーが受信pipeへエンドポイントアドレス`0x82`全体を渡すため、受信pipeには通常の方向ビットに加えてbit22も立つ。記録器と単体検査を修正した。探索記録自体はバッファ上書きがあったため件数の証拠には使わない。

修正版はCH341の前後送受信pipeだけを記録し、CPU別overrun/droppedが全て0で完走した。各アダプターについて、OUT投入/完了は各6006件、IN投入/完了は各3508件。IN実データは各3000件×32バイト＋500件×12バイト＋起動時6件×17バイトで、500周期×12返信＋起動時6返信に対応する。停止時の0バイトINは各2件。USBホスト側ではこの試験中に未完了URBを観測していない。これはType17の正常例であり、過去のType1欠落箇所を特定したものではない。

`xhci_urb_giveback`の`status != 0`フィルターは正常に完了した転送も全件拾ったため、USBエラー数として扱えない。記録器はその二重収集をやめ、バッファを増やし、overrunがあれば不完全とする。URBの投入からIN完了までの時間には、QDD/CANからの返信待ちも含まれるため、USB自体の遅延として引用しない。

STOP返信込みの無駆動試験も試みたが、1回目はTorchのないPython環境で通信前に中止、2回目は現在姿勢が保存済みモデル関節範囲外となり**0周期で中止**した。有効化・学習目標送信はどちらも0。初回の200周期試験は取得専用フラグを使っておりSTOP返信を含まないため、STOP試験の成功数に算入しない。現姿勢の再照合なしに範囲を広げない。

停止した軸は右後付け根ID9で、旧校正の生角約−0.673radから現読値約＋5.633radへ約＋6.306rad変わった。旧オフセットのままではモデル角約＋6.279radとなり、登録範囲±0.5radを超える。操作者は電源再投入後も実物を一回転させていないと確認した。現起動の無出力読取りと診断用プロファイルを照合するとID9のモデル角は−0.0043radで、12軸すべてが登録範囲内に入った。この監査でID9に追加した整数回転は0であり、既存プロファイルのオフセットが現読値を範囲内へ写像している。旧候補とのオフセット差の由来と現物の原点・正方向・電源epochの承認が済むまで、この診断値を実出力補正へ採用しない。他11軸では同じ約2π差は見られなかった。

### 現起動の診断用STOP代理試験

上記の現起動読取りを入力に、ID9を範囲内に写像する診断用プロフィールで100周期の実推論＋STOP代理返信を実施した。全100周期完走、12軸STOP返信確認、モーター有効化0、学習目標送信0だった。取得中央値8.326ms、推論中央値28.729ms（P95 30.765ms）、全体中央値46.191ms、最大48.765msで、20ms以内は未達である。26要求/周期（Type1目標は0）の構成では、取得より推論と返信待ちが支配的であり、現状のまま実出力へ進めない。詳細は[evidence/can-stopproxy-diagnostic-20260929-r3.json](../evidence/can-stopproxy-diagnostic-20260929-r3.json)。

この試験コマンドには`--native-policy-manifest`と`--scalar-step-manifest`を指定していなかった。実行コードはその場合`shadow.load_policy(bundle)`を選ぶため、過去の高速モデルで得た20ms結果との同条件比較ではない。`inference_ms`はモデル単体ではなく入力検査を含む`observer.consume()`全体である。高速モデルの効果を確認する次の無出力試験では、キットr6に保存された`model_manifest.json`（SHA-256 `477d3f83b5f2177b22d5dda69e3884d7e22622a6fefdf7d578d8bd64121609de`）と`scalar_step_manifest.json`（SHA-256 `7ad6670368feb10d36bd62f594c7a53e89f28a5462fd1c3cf2292e2c1987f666`）を両方明示し、`--require-pinned-fast-model`で取り違えを拒否する。開始前に現起動・現40V電源世代の読取りと箱支持を再確認する。実出力へこの診断用枝を流用しない。

## skipの試作仕様

1. 全要求を書き終えた通常周期のみ対象。起動時・部分write・故障返信・切断・不正フレームは停止。
2. 20msを超えたら**目標更新をskip**し、推論も新しいType1送信も行わず、元の未完了要求の返信だけを待つ。再送しない。
3. 追加は最大1周期、仮の上限は周期開始から40ms。直前99周期にskipがあれば次のskipを認めない。
4. 返信が揃っても古い入力で再推論せず、`RESAMPLE_REQUIRED`を返す。新しい全軸・IMU・電圧の検証と継続可能な残り時間が必要。
5. 揃わなければSTOP。セッションのpoison・曖昧な返信状態を消して再開しない。

この40msは**オフライン仮説の上限**。現在のhost watchdog 40ms、sample gap 21ms、sample age 20msとはそのまま両立しない。実出力へ接続する際は、各軸の最終送信時刻から残る時間、再取得・推論・出力の所要時間を含めて上限を切り詰め、モデルの履歴更新も実際の時間経過に対応させる。40msの待機を現行プロファイルへ単純代入しない。skip周期を20ms成功件数へ混ぜない。

検証：Macの解析・状態遷移・実C++ socket通信・USB pipe検査は計74件成功。うち実C++の遅着25ms／末尾2バイト遅着／40msまで無返信の3ケースは、Jetson上でもsocket通信で成功。実機モーターの受信遅着を回復した結果ではない。
