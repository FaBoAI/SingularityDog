# 20ms制御へ向けた別経路の比較 — 2026-09-28

現行の2台のCH341 USB2CANでは、前後CANとIMUを並列に取得し、実際の学習モデルで計算してから、全12台へSTOP代理を送る。R15の同一起動500周期では、**最古入力の取得開始から最後のホストwriteまで**は500/500周期で20ms以内（最大19.334ms）だった。一方、最後のSTOP返信は13/500周期、周期終了は16/500周期で20msを超えた。学習済み目標を送る実制御は要求数と返信処理が異なり、まだこの結果を合格として流用できない。[実測と条件](hardware-native-cycle-20260928.md)

R15の中央値は取得7.036ms、推論区間3.659ms、最終writeまで15.416ms、最後の返信まで18.191ms、周期終了18.561ms。両バスの遅い方の6送信には5間隔×0.8msという約4msの設定待ちがあり、最後のwriteから返信まで約2.77msある。R16では自動GCを止めても周期終了21/500件が20msを超え、その21件はすべて推論区間が5ms以上だった。保存されたR16の時刻から**モデル呼出しだけを各周期3.5ms以下にできたと仮定**すると、他の区間が同じ場合の超過は0/500になる。この再計算は実測の改善ではない。

[RS05公式資料](https://github.com/RobStride/Product_Information/blob/main/Product%20Literature/RS05/RS05User%20Manual260713.pdf)はType24の既定報告を10msと説明するが、返信型の記述には節間の差があり、現物FWの生フレームを優先する。10ms報告を受けるだけで入力が「新鮮」とは限らず、モーター内部のサンプル時刻は現状不明である。前周期のType1返信をそのまま次周期の入力にすれば問い合わせを減らせるが、50Hzでは最古入力から次の送信までの遅延が20msを超え得るため、周期達成と情報鮮度を分けて判定する。

R21の返信後工程がそのままと仮定して、Type24の**ホスト受信時刻**が取得完了時点で何ms前まで許されるかを[保存時刻の解析](../tools/analyze_type24_age_budget.py)で計算した。最古報告→周期終了を20ms以内にする許容年齢は中央値9.18ms、最も厳しい周期6.54msである。これはType24で取得7msが実際に消えるという実測でも、モーター内部サンプルの鮮度保証でもない。既定の10ms報告を受けるだけでは全周期の入力年齢条件は証明できず、12台の報告位相・欠測・報告とSTOPの競合を実機で測る必要がある。

Jetsonの内蔵CANも比較候補だが、[NVIDIA公式資料](https://docs.nvidia.com/jetson/archives/r39.2.1/DeveloperGuide/HR/ControllerAreaNetworkCan.html)ではOrin Nano/NXは1系統で、外付け3.3V CANトランシーバーを要する。現在の前後2バスを両方置換する手段とは扱わない。GPU/TensorRTも[同社の計測指針](https://docs.nvidia.com/deeplearning/tensorrt/latest/performance/benchmarking.html)に従い、バッチ1の転送・起動・同期を含めて比較する。actor単体中央値は保存入力で約0.85msなので、actorだけをGPUへ移しても全工程で必要な約2msの尾部削減を保証しない。

現在の2台は`/dev/ttyUSB0/1`の`ch341`ドライバー（USB ID `1a86:7523`）で、Jetson上に両ポートの`latency_timer`属性は見つからなかった。FTDI用の`latency_timer=1`やSocketCANの`txqueuelen`を現在のシリアル変換器へそのまま適用しない。0.7ms要求間隔は以前23周期後に後脚ID9の返信欠落で中断したため、今回の0.8ms条件を代える根拠にしない。[既存の比較](hardware-native-cycle-20260928.md)

前周期の返信が終わった時点で次のCAN/IMU取得を始める先行取得も[保存時刻のリプレイ](../tools/analyze_cycle_overlap.py)で評価した。各工程の所要時間が変わらない楽観条件では、20msを超える次回取得開始間隔はR15で16→13/499、R16で21→15/499へ減る。6ms先行すれば名目tickからホストwriteまでの中央値は約6ms短く見えるが、**最古入力の取得開始からwriteまでの遅延・入力鮮度は短くならない**。したがって先行取得だけで20ms達成とはせず、入力の時刻を保持して送信直前に鮮度を再検査する。

次の実行順は、(1) 支持台を残した有限回のV3実出力で、統合したR22初期化・STOP・入力鮮度を実機検証、(2) 実学習目標を使う出力経路の要求数・返信・鮮度と次周期開始間隔を測定、(3) Active Reportingの6台開始欠測を受動観測で切り分け、(4) USB待ちの所在が分かってからSocketCANをA/B比較する。同一起動の対照試験も追加し、R22の改善要因を分離する。どの条件でも最古入力→最後のホストwrite、最後の返信、周期終了、次周期開始間隔を別々に報告する。監視閾値や返信照合を緩めて20ms合格とは判定しない。
