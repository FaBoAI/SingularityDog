# STOP再送（2026-09-29）

Type1通信の返信欠落後、STOPを1回送るだけでは全軸の停止確認が揃わない試験があった。操作者の提案に従い、実出力ランナーの終了・異常停止処理へ、回数と時間を限定したSTOP再送を追加した。

| 項目 | 実装 |
| --- | --- |
| 回数 | 前後各バスで最大3回。1回で6軸すべて確認できれば終了 |
| 時間 | 各バス合計500msの絶対通信期限。1回の通信期限は最大250ms。準備時間を除き残り20ms未満なら追加しない |
| 実行順序 | 通常指令をキャンセルし、同じバスの所有スレッドでSTOPを送る。前後バスは並列 |
| 送信内容 | 各回6軸のSTOPのみ。学習目標や有効化の再送はしない |
| 記録 | 各回の送信・受信・期限・断片・曖昧な軸、合計試行回数と期限を保存 |
| 故障・不明な返信 | 以前の回で観測した故障と曖昧さを保持。新しいSTOPの返信と判別できないものは確認済みにしない |
| 最後まで未確認 | `STOP_UNCONFIRMED_POWER_OFF_REQUIRED`を維持し、操作者が40Vを遮断 |

再送は停止命令が届く機会を増やす対策であり、Type1返信欠落の根本原因を解消したとはしない。指令断保護の200ms設定、制御周期20ms、データ鮮度の上限は変更しない。500msは停止処理だけの通信予算で、通常制御の待ち時間ではない。OS停止などによるソフトウェア実行時間や物理的な停止時間を保証する値でもない。

C++は同じセッションを停止処理中も維持する。RS05のType2返信には要求ごとの連番がないため、以前のType1・enable・STOPとの対応が不明な軸について、STOPを送り直しただけで曖昧さを消すことはしない。

ソケット上の実C++通信と実出力ランナーを含む119件のテストが通過した。通常時の1回終了、上限3回、全無応答時の共通期限、以前のType1との返信混同の拒否、古いSTOP返信の拒否、故障値の保持、前後バスの所有スレッドでの実行を確認した。プロフィール・CLI・荷重試験関連の追加146件も通過し、今回の関連検査は計265件成功した。**この修正後の実機再送は未計測**。操作者は40V Off・現物異常なしを確認後、充電完了と報告した。再投入後の状態を確認し、次回はゲインとモデル混合率ゼロで再送結果を確認する。

## 充電後の修正版実機試験

新しい電源投入で12軸UID・角度・電圧を読み、全軸のゼロゲイン通信断保護と終了STOPを再確認した。ID9は生角の枝が−1回転変わり、モデル可動域内の候補が一意になる枝を選んだ。ほかにも姿勢差があるため、旧始点を使わず新しい静止記録で範囲を結び直した。操作者は現姿勢の約±3°の離隔を確認した。

修正版243ファイルをJetson上で照合し、次の2試験をそれぞれ1回実施した。どちらも箱支持、4足接地、送信間隔0.8ms・同時待ち3台・CPU4・演算スレッド各1。CPU設定は終了後に復元した。

| 試験 | 完了周期 | 全工程中央値 / 最大 | 20ms超過 | 終了STOP |
|---|---:|---:|---:|---|
| 全12軸ゼロゲイン・モデル混合率0 | 88 | 18.593 / 19.495ms | 0 | 前後各1回で12軸確認 |
| 学習目標混合率0.5%、Kp3/Kd0.15、最大1°・2秒枠 | 97 | 18.640 / 19.575ms | 0 | 前後各1回で12軸確認 |

両試験で操作者は音声あり・現物異常なしと回答。学習目標側は開始・正常な終了ランプまで完了し、欠番0、開始間隔最大20.003724msだった。初回と開始ジッターの扱いは既存の合意に従う。停止後の読取りでも全軸mode0・電流0、最大角度幅0.01134°を記録した。

**今回、STOP再送ラッパーは動いたが、2回目以降の送信は不要だった。** 以前の返信欠落の根本原因、欠落時の再送効果、長時間の通信安定性を解消済みとは判定しない。学習目標の最大変化は約0.132°、実角の最大変化は約0.066°、読取りトルクの最大絶対値は約0.040Nmであり、荷重立位の証拠でもない。

集計：[支持付き実出力の結果](../evidence/supported-policy-stopretry-20260929.json)。生ログと実行キットはMacの非公開バックアップに保存。Jetson原本は`~/singularitydog-logs/stopretry-zero-type1-20260929-r1/report.json`と`~/singularitydog-logs/stopretry-supported-20260929-r1/report.json`。


## 12cm支持・5秒試験後のSTOP待機延長

その後の5秒試験は、r2が完了200周期後にID6、r3が完了150周期後にID8・12の返信待ちで停止した。r3のID12は17バイト中15バイトが受信済みで、末尾CR/LFが20ms期限に間に合っていない。ID8はその時点で返信を受信していない。完了周期の最大はそれぞれ19.348／19.532msだが、失敗周期を除外して5秒完走や通信安定性の合格とはしない。

STOP時には該当軸のmode0・故障値ゼロの返信があったものの、直前のType1とSTOPの対応が曖昧なため、いずれも操作者に40V Offを依頼した。両回とも操作者は遮断完了・現物異常なしを報告した。

操作者の提案により、停止確認の通信予算を次のように変更した。

| 項目 | 変更後 |
|---|---|
| 最初のSTOP | 各バス合計250msを維持。後ろの軸への初回送信を遅くしない |
| 2回目以降 | 各回最大500ms。残りの合計時間が短ければそちらを使う |
| 回数・合計 | 最大3回、同じ絶対期限で合計1秒 |
| 上位の結果回収 | 前後バス共通1.25秒。停止処理の起動・中断処理の余裕を含む |
| 継続する条件 | 通常20ms、指令断保護200ms、返信の曖昧さ・故障値の保持 |

実C++の模擬通信54件はMacとJetsonで成功した。55msずつ遅れる返信、全台無応答で1秒以内の通信予算、古いType1/STOP返信の混同拒否、初回成功なら再送しないことを含む。1秒を超えた結果回収の扱いも別途検証する。待機延長だけで通信欠落を解消したとはしない。


延長版r5/r6の実機結果では、未確認バスのSTOP処理は約74ms／180msで3回を終えた。1秒の合計予算は使い切っていない。待機時間不足と、以前のType1/enable返信との対応の曖昧さを分けて扱う。起動時の有効化返信を30msへ分離したr6は初期化を通過したが、32周期後にID12の入力返信が欠けた。詳細は[12cm支持試験](ground-support-rehearsal-20260929.md)、[集計](../evidence/supported-policy-box120-20260929.json)。
