# 実機歩行までの課題と解消方法 — 2026-09-24

**次の目標は、正しい実機入力を使い、1つの歩行方策を20ms周期で連続実行し、支持付き立位へ接続することです。** 追加学習の前に、通信・角度変換・荷重下の制御を固めます。現在は実入力による無出力計算まで進み、学習済みモデルでの実機立位・歩行は未実施です。

この文書は最新の優先順位です。[詳細な試験履歴](hardware-countermeasures-20260924.md)、[集計JSON](../evidence/hardware-results-20260924.json)、[接続仕様](deployment-roadmap-20260922.md)と対応します。以下の対策と試験時間は提案であり、完了済み試験とは区別します。

最優先の[取得・推論・送信を20ms以内にする方針](control-20ms-strategy-20260924.md)に、工程ごとの時間予算、通信待ちの新しい解析、小修正と機器変更の判断を整理しました。

21:38 JSTのCAN単独比較では、同じtimeoutの再設定を省くことで取得中央値24.221ms→22.044ms、最大25.683ms→23.039msとなりました。各20巡・492要求／492返信、残留なしを確認。20ms以内は両条件とも1/20巡で、全工程20msは引き続き未達です。下の実入力・推論の表は、このCAN単独比較より前の統合診断の記録です。

## 計算と通信の改善方法

**QDD・IMUの取得開始から、AI計算を経てモーターへ指令を送信し終わるまでの全工程20msは、まだ達成していません。** 最新試験はモーターへ送信しない診断であり、送信込みの所要時間は未測定です。

| 工程 | 最新の確認結果 | 20msとの関係 |
|---|---|---|
| QDD・IMUの入力を揃える | 計算に採用した入力の取得幅37.698ms | 新しい全入力を20ms内で取得できた結果ではない |
| 入力検査・変換・AI計算 | 1条件あたり13.867ms／15.391ms | 取得済みデータを使った処理。純粋なAI部分だけの時間ではない |
| 計算結果をモーターへ送信 | 無出力診断のため未実施 | 送信時間・指令負荷・停止監視を加えた周期は未検証 |
| 全工程の連続実行 | 未達・未検証 | 1tickの部分測定を50Hz制御の達成としない |

取得幅と計算時間は非同期区間を含むため、単純に足した値を実測の全工程時間とはしません。次は入力の元時刻から指令送信完了までを同じ時計で計測します。

最新r4は通常のCPU設定で、入力検査・変換込みの処理がh=0で13.867ms、h=1で15.391msでした。共通予定時刻からの終了はそれぞれ16.623ms、34.388msです。**2仮説を合わせた既存の20ms条件は未達のまま保持します。** h=0が1回20ms以内だったことも、連続実時間動作の証明ではありません。

hは12関節の負荷履歴で、2つの異なる歩行モデルではありません。比較は別試験に分け、本番では検証した1つの履歴を持つ方策を実行する構成にします。ただし、hの実機更新方法が未確定なため、先行する1条件の速度測定は引き続き無出力の診断です。

全工程を「要求待ち→USB送信→受信→解釈→時刻付き状態→方策→指令生成・送信」に分け、中央値・上位百分位・最大・期限超過数・欠測数を記録します。時刻を書き換えて古い標本を新しく見せたり、遅れた指令をまとめて送ったりしません。ログ書込みは制御区間から分離します。

受信と方策を非同期にしても、古い入力が新しくなるわけではありません。最新r4の取得幅は37.698ms、処理開始時の最古入力は41.084ms／57.324msです。現在の100ms許容は無出力診断用で、歩行に使える遅延を実証した値ではありません。入力保持を使う場合は、その遅延と時刻差を再生・シミュレーションへ入れて成立を検証します。

CAN側の1Mbpsと、Jetson―変換器間のUART 921600bpsは別設定です。実CANビットレートを確認したうえでUSB転送・バッファ待ちを測ります。2台化は完了しているため、追加購入より先に現在の遅延箇所を特定します。変換器が支配的なら、拡張CANフレームとRS05との互換性を確認したSocketCAN対応機器を比較候補にします。出力指令が加わった際の通信量も別途検証が必要です。

## 荷重の切り分け

付け根には脚全体の重さが掛かります。URDFに基づく水平姿勢の見積もりでは約0.527Nmですが、現物の実トルクや当該試験姿勢の値ではありません。満充電でも同じ固定目標の誤差1.638°が残ったため、充電だけではこの誤差を解消できませんでした。ゲインを上げ続ける前に、質量・姿勢・トルク換算を照合し、補償を比較します。

## 効率を上げる実施順

1. **20msの内訳を計測する。** QDD・IMUの元時刻から、入力処理・推論・指令生成までの区間計測を用意します。送信込みの検証と、現在の無出力診断は別の結果として記録します。
2. **ソフト側を並行作業にする。** 通信の区間計測、C++処理、hの更新式、RS05換算、共通停止を保存ログ・テストで準備します。この間、操作者が姿勢を保持する必要はありません。
3. **現物確認をまとめる。** 校正は疑わしい軸だけ、L字と既知方向を続けて記録。IMUも未確認方向だけ確認します。4脚同時にL字を保持する手順には戻しません。
4. **1条件の無出力連続実行。** 初回は10秒、成立後に60秒へ延ばす提案です。開始前に20ms期限、入力鮮度、状態更新、停止条件を固定します。結果に合わせた閾値変更はしません。
5. **支持下で1脚保持・全12軸停止を確認。** 既存条件で付け根の未達を解消し、通信断・プロセス終了時の解除も実測します。
6. **支持付き固定立位→方策への切替→短い低速前進。** その段階で機体重量・重心・関節応答・通信遅延が学習条件を外れるなら、実測をシミュレーションに反映して再評価・追加学習します。

起動確認・個体照合・電圧・入力範囲・周期集計を一括ツールにまとめ、保存先と合否を1枚の表へ出す方針です。操作者への確認は、手で動かした後の手離しや新しい駆動段階など、現物情報が必要な場面へまとめます。立位・歩行への進行は上記の成立条件で決めます。

## 最新計測の証拠と限界

- 通常CPUの実入力r4：両条件とも1tick計算、時間条件で採用できたtickは0、モーター出力0。同一起動中に終了し、IMU設定復元、取得終了、ポート・排他解放、ログ保存を確認。
- CANは225完全送信／223受信。中断時に前脚側の速度返信2件と残留34bytesがあり、完全な通信完走とは扱いません。これだけで恒常的な通信欠落とも断定しません。
- 生入力監査：IMU10標本、関節211標本、元時刻と変換を照合。監査SHA-256：`d8bebfe26545586c7f2b4e64f3ffa826289c5ec3f3c1fe87ddc46b8d08a8aac0`。
- 1tickの成功部分、保存入力での高速化、各脚の相対動作を、連続50Hz・荷重立位・学習済み歩行の成功へ読み替えません。
