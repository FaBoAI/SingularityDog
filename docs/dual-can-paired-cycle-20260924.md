# 前後CANの開始時刻を同期 — 2026-09-24

**全12台の角度・速度取得幅は中央値31.559ms→24.339msへ約23%短縮しました。** 主に前後バスの開始ずれを解消した効果です。各バスの処理自体は約23msのままで、50Hz制御は未達です。

同じソース・起動セッションで、従来の独立巡回、開始同期付き巡回の順に1回ずつ測定しました。各20巡、識別12件と角度・速度480件の計492要求・492応答です。要求窓4、送信間隔の設定0.5ms、UART 921600bpsを維持。CANビットレートの変更や確認は行っていません。

| 指標 | 独立巡回 | 開始同期付き |
|---|---:|---:|
| 全24項目の取得幅・中央値 | 31.559ms | 24.339ms |
| 全24項目の取得幅・最大 | 36.032ms | 26.632ms |
| 前後の読取り開始差・中央値 | 8.342ms | 0.308ms |
| 前バスのみの取得幅・中央値 | 23.040ms | 23.376ms |
| 後バスのみの取得幅・中央値 | 22.800ms | 23.698ms |
| 全24項目の取得幅が20ms以内 | 1/20巡 | 4/20巡 |
| 隣接する巡の読取り開始間隔・中央値 | 23.504ms | 25.053ms |

取得幅は、各巡の最初の実要求から最後の実応答までです。**同期するとデータの時刻が揃いやすくなりますが、巡回開始間隔は今回むしろ長くなりました。** 待ち合わせへの先着から最後の応答までは中央値25.488ms、最大27.897ms。ゲート待ち時間は前バス中央値0.699ms、後バス0.071msです。待ち時間を除いた取得幅だけで周期達成とは判断しません。

## 実装・検証

`dual_can_pipeline_benchmark` に任意の `--paired-cycle-sync` を追加しました。両バスの識別確認後、前巡の処理が完了した2系統を各巡の先頭で待ち合わせます。待ち合わせは250msまたは残り実行期限までで、片側失敗や取消で両側を終了します。既定の独立巡回は維持しました。

関連69オフラインテストと独立レビューが合格。既定経路は旧版との16条件比較でも一致しました。実機記録は生フレームから独立検算し、両条件とも正規のType0／17だけで、個体照合、492応答、残留なし、ポート終了・共通排他解放が一致しました。この試験の角度・速度だけでは脱力モードや電圧は証明できません。

## 残る修正

- 各バスの約23msを、送受信・ポーリング・OS設定呼出し・時刻確認に分解する。送信間隔を短くする前に、既存の欠損・期限検査を維持して負担を特定する。
- 現機のCH341ドライバーには `latency_timer` がなく、FTDI向け設定は適用しない。pyserialのtimeout設定が繰り返しOS確認を呼ぶ点は調査候補で、USBのボーレート再設定が毎回発生しているとは判断しない。
- CAN単独の改善後、IMU・推論・出力・共通停止を含む20msの検証へ戻る。今回はIMUアクセスも推論も駆動もない。

各条件1回の短い比較で、長時間の遅延上限や実時間制御は保証しません。遅延した同じ種類の応答を前巡から完全に識別できることも未証明です。
