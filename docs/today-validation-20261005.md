## 加速度約+8.8%の原因監査

A/B/Cの6,771行は、rawから`9.80665/16384`を掛けたSI値と完全一致し、読戻し`ACCEL_CONFIG=0x21`・±2g、飽和なしだった。保存済み±2g→±4g→±2gもrawほぼ半減・SI一致で、レンジ依存の換算ミスでは説明できない。trimは前後・過去資料と一致し、書込みなし。self-test参照値は収録したが、実際のself-testは未実施。ドライバのmock検査24件も合格した。換算とoffsetレジスタの形式は[TDK公式データシート](https://product.tdk.com/system/files/dam/doc/product/sensor/mortion-inertial/imu/data_sheet/ds-000189-icm-20948-v1.5.pdf)と照合した。

今回のノルム偏差を説明できる具体的なソフト不具合は見つからず、加速度補正は適用していない。実効bias、感度、trimの妥当性、組立や電源などの要因は分離できない。同じ固定姿勢の反復では3軸bias／scaleの識別情報が増えず、水平付近の小傾斜も鉛直軸scaleを分離しにくい。固定取付のまま十分に異なる既知重力方向と別収録の検証が必要だが、今の箱支持と精度不明の気泡式水準器はその条件を満たさない。取り外し・機体反転・六面を必須にせず、未知の器差や原点精度を0へ置き換えない。[監査範囲](../evidence/validation-live-timing-20261005.json)。

## 高速の無出力一括計測

まずデバイスを開かないplanを表示する。Jetson上のキットのtoolsから実行し、`DOG_WORK` にビルド成功のstate、`DOG_SCALAR_MANIFEST` と `DOG_SCALAR_SHA` に検証済みの対象Jetson用scalarモデルを指定する。自動fallbackはない。後から追加した以下の100µsオプションは新しいソース用であり、保存済みr2キットへ後書きしていない。更新版を別の新しいキットへ固定してから使う。

```bash
python3 tools/dog_tomorrow.py diagnostics \
  --work-dir "$DOG_WORK" --timing-mode v3-overlap \
  --python-switch-interval-us 100 \
  --scalar-step-manifest "$DOG_SCALAR_MANIFEST" \
  --scalar-step-manifest-sha256 "$DOG_SCALAR_SHA" \
  --request-gap-us 900 --request-window 3 --policy-cpu 4 --cycles 501
```

機体の箱支持・4足接地・QDD停止・手離し・即時40V遮断と、他ツールの停止を確認後だけ、同じ引数へ `--execute --supported-disabled` を加える。短い事前試験は `--cycles 5`、次に50、最後に501。順序はcapture→監査→CAN取得→静止Type17/Type2比較→実推論STOP代理。どこかで失敗したらその実行を中断し、旧成功へ戻さず保存する。

`--python-switch-interval-us 100` は `full`／`diagnostics` の `--timing-mode v3-overlap` 指定時だけ使用できる。`diagnostics` のcapture・CAN取得・静止比較は変えず、full段の実benchmark子へ既存の切替wrapperを適用する。plan・stage・最終summaryに指定値とwrapper SHAを記録し、子の終了時に元の切替値へ戻す。指定なしの既存挙動は変更しない。関連61件のソフト検査と独立レビューが合格した。要求したwrapperの正規パス・通常ファイル・SHAをfull子の開始直前と終了直後に再検査し、途中の変更でfullの開始やstate昇格を拒否する。r3の一括入口はcapture・compareを実行したが、比較BLOCKEDでfull段は未実行。r2／r3の20ms表は既存benchmarkを明示した別scopeのcharacterizationであり、一括比較のBLOCKEDを解除する根拠にはしない。

高速設定は26要求、C++ scalarモデル、ordinary voltage overlap、200µs待機、単一数値計算スレッド、起動時warmup、CPU4とI/O workerの分離、周期中GC延期、CPU/壁時計計測を明示する。CPU周波数やSuper Modeをこの入口で永続変更しない。pipelineフラグも追加しない。

**STOP代理は学習目標の実送信ではない。** ベンチマークのordinary overlapは各バスのfeedback後すぐに電圧を取得する。正式実出力のpipeline=falseは前後feedbackとIMUを集めてから電圧を始める。待機・モデル・26要求の比較として使い、実出力の同一dispatchを証明したことにしない。後の支持付き実出力でその経路を測る。

`COMPLETE_DIAGNOSTIC` は計測の完了であって20ms合格ではない。`steady_timing`、`host_deadline_misses`、`iteration_deadline_misses`、`whole_iteration_ms`、最終返信、開始間隔、未完了のfailure recordを合わせて読む。失敗した周期は成功周期の分位値に含まれないため、最大値だけを抜き出して成功にしない。初回超過を別扱いにしても、入力鮮度や返信欠落を許可したことにはならない。

## 返信欠落とUSBを同時記録する

既存の `tools/capture_xhci_metadata.py` は受動的なホスト転送記録。必要なtrace権限がある端末で、対象2台のUSB topologyを実物へ照合して指定する。

```bash
sudo -n python3 tools/capture_xhci_metadata.py \
  --usb-device "$DOG_FRONT_USB_TOPOLOGY" --usb-device "$DOG_REAR_USB_TOPOLOGY" \
  --seconds 30 --output "$DOG_USB_OUTPUT"
```

`USB_TRACE_READY` の後で、現物確認済みのゼロゲイン診断を開始する。Enterや音声を待つ間に30秒を使い切らない配置にする。自動でEnterを送らない。終了後に、最初のCAN送信から最後のSTOP返信までのmonotonic時刻をtraceが覆うこと、`trace_lossless=true`、`instances_removed=true` を検査する。範囲不足・lossがあれば部分記録として保存する。traceを付けた時と付けない時の20ms測定を分ける。

失敗した診断の保存reportを、通信しない解析へ渡す。

```bash
PYTHONPATH=runtime:. python3 tools/analyze_motor_reply_failure.py \
  --report "$DOG_REPLY_REPORT" --expected-sha256 "$DOG_REPLY_SHA256"
```

新ログのreader counterからEOF・EINTR／EAGAIN等・期限までread bytesなし・partial/backlogを分ける。古いログはcounter未記録と表示する。USB OUT成功はホスト転送の事実で、USB2CAN内部のUART、CAN線、QDDまで届いた証明ではない。later mode=0を、欠落した同一Type2の取引へ割り当ててSTOPを確定しない。
