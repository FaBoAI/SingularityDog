最後の返信までは、この後にそれぞれ2.721ms／2.717msかかる。「その他のホスト処理」には必要な検査、受信デコード、ログのメモリコピー、OSの実行待ちも含み、全量を削減できるという意味ではない。前後のバスは同時に動くため両者を足さない。返信末尾の時間からUSB基板だけの遅延を断定することもできない。

現行のselect待機は既に送信可能時刻までに打ち切る実装で、固定3msのsleepを除くという修正は該当しない。次の修正候補は、送信バイト列・固定の記録項目を0.6msの待機中に準備し、実write直前の返信対応・期限・取消・17バイト検査・起動確認を維持する方式。まず待機復帰、ログ作成、ガード、実writeを個別に計測し、削れる費用を確定する。3回目の前脚送信ではintent→writeの合計0.860msのうち起動確認が0.662msで、残る0.198msがその区間の記録などに相当する。準備の前倒しだけで残り1.865msを回収できるとはまだ主張しない。
