# 待機スレッドの比較 — 2026-09-25

**2msごとの待機を期限付きの1回待機へ変えるだけでは、残り約4msを短縮できる結果は得られなかった。** 保存入力を使った推論・検査・変換の中央値は4.123msから4.121msで、差は約0.002msだった。実機全工程の最新値は引き続き中央値22.283ms・最大23.193msであり、20ms未達。

3つの新しいプロセスで各20組を交互・逆順に実行した。各プロセスは同じleanモデルと10回warmup、各呼出し前reset、同じ保存入力を使う。全180回で保存出力、modelの全parameter/buffer、observer状態、入力の時刻・ハッシュが一致した。待機スレッドは全件終了した。

実機統合測定と同じくCPUを既存周波数上限1,497,600kHz内のperformanceへ一時変更し、終了後に親・watchdog・外部読取りでschedutilへの復元を確認。電力モードと周波数上限は変更していない。

これはCPU内の待機競合を切り分ける比較で、通信・IMU・送信は含まない。通常のEvent待機も通知されれば2ms満了前に起きるため、2msを取り除けばそのまま2ms短縮するという解釈は誤り。期限付き通知待機の実装候補は120件中119件成功・既存記録不足1件skipだが、この比較を理由に現行計測へ採用しない。

次は入力組立ての重複コピーと、準備中の待ち時間後に推論が遅くなる可能性を、保存入力のまま比較する。保存入力の時間を実機全工程から差し引いて達成とは扱わない。
