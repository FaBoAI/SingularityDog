# Jetsonの20ms検証で毎回参照する成功設定

2026年10月7日のユーザー指示「成功時と揃えた設定は今後毎回使うので毎回参照」を保存する。以後、実機のタイミング検証はこの文書と[設定・証拠JSON](../evidence/jetson-best20-settings.json)を先に読み、基準からの変更を明記する。

現在の基準は、新R4ソース・現在の保存角度へ参照を結び直したprofile・通常Python observer・明示選択したFKモデルによる無出力STOP代理診断。新参照の5→501周期は定常最大19.640373／19.804874ms、処理超過・予定期限超過・スキップはゼロだった。同じR4の旧参照は定常最大19.614874／19.837018msだったが、profileが異なるため、同一profileの501周期再測定には数えない。過去のR2の501周期2回は定常1,000周期すべて20ms以内、各回の最大19.831329／19.888924ms。R3の501周期は定常最大19.872634ms、処理超過・スキップはゼロ、初回の遅れを引き継いだ予定期限超過1回を保持する。R2・R3・R4を別のsource枝として保存し、R2の再測定2回成功を現在のR4成功2回には読み替えない。初回1周期は別集計する。これは有限時間の実測で、将来の最悪時間や実Type1出力の保証ではない。

## 毎回揃える条件

| 項目 | 基準 |
|---|---|
| 制御周期・初回 | 20ms。初回1周期を保持して別集計、定常を除外・切捨てしない |
| CAN要求 | `--request-gap-us 900 --request-window 3`。前後2系統、各周期26要求 |
| 一時性能設定 | `jetson_latency_power_scope.py --diagnostic --with-cpu-performance`。CPU最低周波数を利用可能な最大へ、C7を全6 CPUで無効化、EMC最低を現在の最大へ。実測機ではCPU1.728GHz／EMC3.199GHz |
| 維持・復元 | WFI・他のidle状態、電力モード、governor、EMC最大を変更しない。元のCPU・C7・EMC設定を終了後に読み戻して復元確認 |
| CPU配置 | Python起動前に `taskset -c 0-4`。mainはCPU4、3 workerはCPU0〜3。CPU5をworkerへ含めない |
| Python・優先度 | 子プロセスのswitch interval100µs、nice −10。権限を下げるwrapperでは外側の `sudo -n nice -n -10` で先に設定し、権限変更後の実子プロセスが−10を読み戻してから開始する。終了時switch intervalを復元 |
| 数値演算 | `--single-thread-math`。Torch import前のOMP／OpenBLAS／MKL threads=1、Torch intra／interop threads=1 |
| GC・事前推論 | `--setup-gc before-warmup --pre-cycle-policy-warmup-calls 10 --post-pin-policy-prime-calls 10 --defer-gc-during-cycles`。prime後にobserverをresetし、GC設定を終了時に復元 |
| 周期開始・timer | `--absolute-epoch-cadence --release-spin-us 500 --timer-slack-ns 1000` |
| 電圧の並列処理 | `--v3-voltage-proxy --v3-voltage-overlap --v3-voltage-fast-pipeline --v3-voltage-validation-overlap --prepare-voltage-before-feedback-publication` |
| 記録 | `--record-storage trace --output-dispatch-trace --inference-thread-cpu-trace`。初回・定常・未完了周期・原返信・復元を保持、周期内disk書込みなし |
| モデル | `--active-fk-profile`とSHAで現profileへ明示結合。FK artifact SHA `23b40c517b4351cd4c52458e142eb4580546379775afa5c5ced1d0e6db8a6be6`。`--require-pinned-fast-model` |
| 診断の範囲 | `--mode stop-proxy --supported-disabled`。有効化、Type1、学習目標、正のゲインは送らない |

10月8日の新5周期では、性能wrapperが先に権限を下げたため、内側のnice −10設定が拒否されていた。完走した原票は比較条件の相違として残し、基準成功へ加えない。以後、niceは権限変更前に外側で設定し、変更後の実UID・GID、nice −10、Python開始前CPU0〜4を読み戻す。実測値が一致しなければCAN／センサー計測へ進めない。単に起動コマンドへniceを書いたことを設定成功と判断しない。

性能設定・CPU配置・GCを同時に揃えた結果であり、単一要因の原因確定ではない。旧R49のC snapshot複製、retain-GIL copy、native boot guard、新98値変換、通知待ち、phase-owner候補は現在の基準へ自動採用しない。[過去の比較と失敗](20ms-cause-investigation-20261006.md)も保持する。

## 起動前の照合と入口

現起動、モーター電源区間、12軸UID、角度、電圧、機体状態を新しい原票へ結ぶ。過去のIP・起動・電源・姿勢や承認を転用しない。実行するsource inventory、model／native library、profile、校正候補と入力SHAを固定し、絶対原点・符号・モデル範囲・鮮度・電圧・トルク・STOP監視は変更しない。

新キットの準備は[既定PLANの入口](../tools/prepare_jetson_fk_test_kit.py)で先に確認する。次は一般形の**ファイル専用PLAN**で、実際の絶対パスを環境変数へ設定してから使う。`--build`も実機計測の`--execute`も含まない。

```sh
: "${TASK_REPOSITORY:?Set the absolute repository path}"
: "${TASK_PRIVATE_OUTPUT:?Set a fresh private absolute output path}"
python3 -B "$TASK_REPOSITORY/tools/prepare_jetson_fk_test_kit.py" \
  --repository "$TASK_REPOSITORY" --output "$TASK_PRIVATE_OUTPUT"
```

無出力計測は[現benchmark](../runtime/singularitydog_hw/native_pipeline_benchmark.py)の既定PLANを、現入力・全SHA・明示選択で検査してから同じ引数へ`--execute`を追加する。実際の子プロセスはswitch interval100µsを設定・復元する固定sourceのforeground入口を使用する。CPU設定の外側wrapperと`taskset`も実行原票へ記録する。既定PLANを計測成功として数えず、private launcherの古いパスをそのまま再実行しない。[10月7日の手順](today-validation-20261007.md)と[10月8日の修正・準備](today-validation-20261008.md)を参照する。

比較は5周期→初回1＋定常500周期→同条件の再測定。処理時間、予定期限への余裕、スキップ、開始間隔、取得・推論・返信・後処理を別々に集計する。各周期の12軸STOP代理返信は、別の終了STOP確認とは区別する。

旧参照を使った新R4の箱支持2秒試験は96周期を正常終了し、全周期最大19.858123ms、定常95周期最大19.838954ms、20ms超過と後段遅れ許容の使用はゼロ。68回のモデル呼出し、学習目標送信、正常なゲイン下降、全12軸STOPと設定復元を原票で確認した。ユーザーも音声・現物異常なし・状態維持を直接確認した。試験範囲はR3と同じ0.5%・最大1°・Kp3／Kd0.15。

## 10月8日R15：900µsの通常直接経路

同じ性能条件で、native pairと7要求prefixを使わず、元の6軸取得＋別電圧取得の3 worker経路を測定した。501周期×2の定常1,000周期で全処理と予定期限の超過ゼロ、最大19.966437／19.972996ms、最小予定余裕17.352µsだった。原通信26,052要求・返信と復元を独立確認した。[現在の証拠](../evidence/validation-execution-20261008.json)の `latest_unpaired_disabled_comparison_r15` と[原票の集計](today-validation-20261008.md#r15従来の6軸取得別電圧取得を直接つなぐ比較)を参照する。

これは無出力の有限比較で、実出力の2 owner経路とは同一ではない。次の診断はこの直接経路・900µs／window3／元20ms期限を優先する。古いnative pair枝の資格、別のモデル候補、実Type1や終了STOPへ数値を転用しない。開始間隔の小さな超過と過去の中止原票を保持する。
