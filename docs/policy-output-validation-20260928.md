## まず実行できるコマンド：ファイル確認だけ

リポジトリ、または準備したプライベートキットのルートをカレントディレクトリにします。Jetson側でも同じ相対構造を使います。以下はシリアル・I2Cを開きません。

```bash
export PYTHONPATH=runtime
POLICY_TRIAL_DIR="$HOME/singularitydog-logs/policy-output-20260928"
mkdir -p -m 700 "$POLICY_TRIAL_DIR"
python3 -B -m singularitydog_hw.policy_live_profile \
  --write-template "$POLICY_TRIAL_DIR/profile.json"
python3 -B -m singularitydog_hw.policy_output \
  --profile "$POLICY_TRIAL_DIR/profile.json"
```

期待結果は `PLAN_ONLY`、`output_allowed=false`、`hardware_opened=false` です。テンプレートは既存ファイルを上書きしません。2回目は作成コマンドを省きます。

テンプレートの `approved_for_supported_policy_output` を単独で変更しても実行できません。12軸の数値、モデル・校正・IMU・無出力診断のハッシュ、現物レビューが一致する必要があります。記録から確定できない値は推測で埋めず、`blockers` に残します。

新しいプライベートキットでは、診断用通信・実出力用通信・native推論をJetson上でまとめてビルドできます。モーターは動かしません。

```bash
python3 -B tools/dog_tomorrow.py build --execute
```

Macで作った `.so` はJetsonへ流用しません。学習モデルのマニフェストと実出力ライブラリの照合結果を成功時の`state.json`に保存し、プロファイルへ結び付けます。キット以外で実出力通信だけをビルドする場合は`python3 -B runtime/experiments/native_active_transport/build.py`も使えます。

周期計測は最後の返信受信で終わらせず、その後の12軸の復号・安全値検査・計測行の組立までを`iteration_ms`に含めます。`output_reply_end_ns`、`output_exchange_return_ns`、`end_ns`を分け、`post_output_processing_ms`で返信後の処理時間を確認できます。最後のゲインゼロ周期も新しい時刻で期限を検査します。最古入力から最終ホスト送信までの値は別に残し、USB送信・返信待ちとCPU側の時間を比較できます。

## 実機で進める順序

| 順序 | 一括で行うこと | 終了条件 |
|---|---|---|
| 1 | 12台のUID・原点候補・符号・現物範囲と過去ログを照合 | 未確定の軸・項目だけを残した一覧になる |
| 2 | 現在の起動・40V電源世代で12軸の読取り、IMU、無出力の連続診断 | 同じモデル・設定・入力の記録が揃い、最大値と超過数が分かる |
| 3 | 残る現物確認、QDD watchdogの動作確認 | 数値の読返しと実際の無効化を区別した記録が揃う |
| 4 | プロファイルとレビューを確定し、ファイルのみの再検査 | 未承認項目ゼロ、SHA256・12個体・組立・電源世代が一致 |
| 5 | 支持・接触なし・即時40V Offを一度確認し、音声付き12軸試験 | 正常ramp完了、全軸STOP返信、故障なし、実物に滑り・接触・異音なし |
| 6 | その1回のログをまとめて判定 | 進める項目と修正が必要な項目が明確。自動再実行はしない |

手作業のたびに12軸全てを取り直す必要はありません。UID交換、組立変更、符号・範囲の未確認など、根拠が変わった部分を再確認します。一方、Jetsonの再起動と40Vの電源世代は別物なので、起動IDだけで角度の360°分岐を保証しません。実行開始時に一意の分岐を選んだ後は固定し、駆動中のジャンプを `%360` で隠しません。

## 承認済みプロファイルが揃った後の実出力入口

次は将来の実行形式です。`<...>` は、確認済みのパス・ハッシュ・電源世代に置き換える項目です。**現状の未承認テンプレートではこのコマンドはモーターを開く前に拒否されます。**

```bash
PYTHONPATH=runtime python3 -B -m singularitydog_hw.policy_output \
  --profile '<承認済みprofile.jsonの絶対パス>' \
  --execute-supported --support-in-place --cutoff-ready \
  --front-port '<前脚のUID照合済みUSB2CANポート>' \
  --rear-port '<後脚のUID照合済みUSB2CANポート>' \
  --library runtime/experiments/native_active_transport/libdog_active_transport.so \
  --power-epoch '<プロファイルと一致する現在の40V電源世代>' \
  --audio '<テスト開始しますの音声ファイル>' \
  --audio-sha256 '<音声のSHA256>' --audio-device '<確認済みALSAデバイス>' \
  --output "$POLICY_TRIAL_DIR/run-001"
```

出力先はGit外の新しいディレクトリです。試験は有限時間で自動終了します。通常の中断要求は `SIGUSR1` に対応し、現在の指令速度から減速してゲインを下げます。`Ctrl+C`／`SIGTERM` は異常停止として両バスへのSTOPを優先します。対象プロセスを取り違える可能性がある一括 `pkill` は使いません。

正常停止に確保する時間は、各軸の `max_command_velocity_rad_s / max_command_acceleration_rad_s2` の最大値と `stop_duration_s` の合計です。起動・モデル出力を混ぜる時間・終了時間を試験全体に収めます。途中で通信・範囲・トルクなどの異常が起きた場合、この滑らかな停止経路は使わず即STOPします。

## 最終表示の読み方

| 表示・記録 | 意味と次の操作 |
|---|---|
| `COMPLETE_SUPPORTED_OUTPUT` | 支持を残した試験のソフト判定が完了。実物の異常なし確認とログ確認を併せる。自立・歩行の合格ではない |
| `ABORTED` | 途中の条件で停止。`errors` と最後の返信を見て原因を1つずつ直す。自動再試行しない |
| `ABORTED_STOP_FAULT` | Mode0の停止返信は来たが故障ビットが残る。停止確認を正常動作の合格に読み替えない |
| `STOP_UNCONFIRMED_POWER_OFF_REQUIRED` | 少なくとも一部の停止返信がない、または帰属が曖昧。支持を維持し、40VをOffにする |
| `motor_enable_attempted` / `motor_enable_sent` | 有効化の試行と、実際にType3をホストが書いた証拠を区別する |
| `command_output_sent` / `motion_gain_sent` | Type1の書込みと、KpまたはKdが正の指令の書込み。学習モデルの寄与とは別に記録する |
| `learned_targets_attempted` | 学習モデルの混合重みが正の段階で送信を試みたか。実際の書込みとは区別する |
| `learned_targets_sent` | その段階のフレームをホストが実際に書いた証拠。混合重み0の開始保持や、目標への物理的到達とは区別する |
| `deadline20ms_misses` | 20msを超えた周期数。中央値だけで達成扱いにしない |
| `full_controller_50Hz_verified=false` | 実機での継続運転は未承認。今回のランナーは完走してもこの値を自動承認しない |

推論やIMU呼出しが止まった場合、独立したホスト監視がCAN所有スレッドへSTOPを依頼します。モデル・I2C呼出しが永久に戻らなければ、画面の最終表示やプロセス終了は待ち続ける可能性があります。USB断線・OS停止・電源断ではホストのSTOPが届かないため、実測済みのQDD watchdogと残した胴体支持が必要です。画面が戻るのを待つことを電源遮断の条件にしません。
