## 短い入口

Jetsonへコピーしたキットのルートで実行する。`python3` は既存のCPU PyTorch環境のPythonを使い、buildと後続で同じ環境を使う。ポートや設定はキットの`kit-config.json`、出力先はGit外の私有ディレクトリを使う。

```sh
# まず計画表示。どちらも機器を開かない。
python3 -B tools/dog_tomorrow.py build
python3 -B tools/dog_tomorrow.py diagnostics

# ソフトの一括ビルド。モーターを動かさない。
python3 -B tools/dog_tomorrow.py build --execute

# 操作者が支持・脱力を確認した後の一括診断。
python3 -B tools/dog_tomorrow.py diagnostics --execute --supported-disabled
```

9月28日のType17取得では`--request-window 3 --request-gap-us 1000`を指定した。`can/compare/full/diagnostics`に同じ形式で渡せる。一括診断の3段階には同じ指定が入る。複合返信の`full`だけ0.8msへ変更した100周期比較と、Type17取得の1.0ms条件を混同しない。0.7msは取得途中にID9が欠測し、完了23周期の統計だけでは採用しない。CPU performanceとtimer slackの比較は別の有限実験で、標準コマンドはこの2設定を変更しない。r7では3スレッドの準備を周期前に済ませ、別の`worker_startup`記録へ保存する。周期内の実取得・推論・出力・返信後検査は計時から除外しない。

実出力・地上試験には通信設定を固定するV2を追加した。`request_gap_us`と`request_window`をレビュー対象のハッシュへ含め、CLIの指定が設定と違えば機器準備前に拒否する。通常送信と緊急STOPも同じ間隔を使う。V1の既定600µs／上限3と旧ハッシュは維持した。今回の統合282テストと、重複する対象を含む別の31件の設定照合テストが通過した。2つの件数は加算しない。

選択式V3は各バスの取得を6軸feedback＋巡回電圧1件とし、周期全体を28→26要求へ減らす実装が完了した。全12軸の初期watchdog設定・読戻しを維持し、音声後・最終姿勢／IMU再取得前に全12軸を再照合する。周期中の`can_timeout`設定変化の巡回検出は省くため、新しい設定レビューにこの監視範囲を明記する。モード・故障・速度・トルク・温度・鮮度・追従・可動域、各周期の電圧と全軸STOP検査は維持する。cadenceと関係9ソースのSHAを設定ハッシュへ固定し、V2の承認を流用しない。適用済みソースで統合208件が通過したが、既存テストを含むので以前の件数へ加算しない。26要求のSTOP代理周期は実機測定済みだが全工程500周期すべて20ms以内には未達で、学習目標のType1実送信は未測定。既定はV2のままである。[要求数とレビューの違い](active-loop-latency-budget-20260928.md)を参照する。

`diagnostics`は毎回新しい取得と新しい保存先を使う。前回の失敗や古い成功状態から自動再開しない。静的Type17/Type2比較の不一致は`DIAGNOSTIC_BLOCKED`として対象IDを示し、後段の推論へ進めない。これは機械故障の断定でも、動的速度・トルク換算の承認でもない。`full`は取得と実モデル計算後にSTOP代理を送る診断であり、学習目標を送信しない。

設定組立は機器を開かない。以下の`<...>`を実際のファイルへ置き換える。これは上限3・800µsの診断を同じ条件の**未承認候補**へ結び付ける例で、2つの通信オプションを省いた既定は上限3・600µsである。診断の値から自動選択しない。

```sh
python3 -B tools/prepare_supported_profile.py \
  --calibration '<今回のcalibration.json>' \
  --source-capture '<同じ取得のcapture.json>' \
  --angle-profile '<保存記録をレビューしたangle-profile.json>' \
  --mount '<取付候補.json>' --bias '<gyro-bias候補.json>' \
  --model-manifest '<今回buildのmanifest.json>' \
  --bundle inputs/policy \
  --pipeline-diagnostic '<今回full/report.json>' \
  --request-window 3 --request-gap-us 800 \

  --power-epoch '<今回の40V電源世代の識別名>' \
  --output '<新規の私有ディレクトリ>'
```

`profile.json`、`hardware-review.json`、`group-settings-template.json`、`preparation.json`を保存する。3群の設定を埋めたファイルは`--group-settings`でまとめて適用できる。通信設定のCLI指定とgroup設定が矛盾すれば拒否し、V2候補と診断の間隔・上限も照合する。未測定の原点誤差・機械範囲・ゲインは空欄を保持する。`UNAPPROVED_ASSEMBLY`は準備成功であり、実出力の許可ではない。

上のコマンドは既定V2候補を作る。V3の26要求候補を作る場合だけ、`--profile-schema singularitydog.supported-policy-profile.v3`を明示して追加する。新しい配布キットのソースpin・設定レビュー・地上試験のprofile参照を結び直し、未承認候補から自動で実行しない。V3を選んでも送信間隔・上限を診断結果から自動変更しない。

保存入力だけのCPU・GC比較も完了した。推論120回で出力・内部状態が厳密一致し、GCのobserve120回／defer120回は自動イベント0だった。後続の実機全工程GC比較は各100周期完走し、通常GCの11回の回収は超過3周期と重ならず、GC延期も初回推論で1周期超過した。GC無効化は採用していない。別のテンソルview再利用候補は保存入力各120回で厳密一致し、推論中央値を約0.14ms短縮した。実機の回収・受渡し区間と、この候補の明示的な診断比較を次に行う。CPU・timer・GC設定の恒久変更や、未完了の試行の採用は行わない。

その後のr8・r9は[全完了条件を記録](hardware-native-cycle-20260928.md)した。r8の自然GC観測では世代1回収が超過へ重なり、以前の世代0のみの観測をGC全般の否定には使わない。準備時GCの100周期は合格したが、500周期にはGCとモデル呼出しの超過が残った。GC延期とCPU固定は改善として採用しない。

r9の診断CLIへ`--setup-gc before-warmup`を追加した。指定した場合だけUID照合・IMU開始後、warmup前にGCを実行し、その準備時間を別記する。実測は約128msで、周期中のGC設定は変えない。既定では実行せず、通常の一括ツールへ暗黙に適用しない。CLI58件と、重複コピー削減の対象50件は通過し、183保存フレームの2入力経路・h=0/1で出力・状態・拒否記録の厳密一致を確認した。件数は既存範囲と重なるので合算しない。r9の通常GC・CPU区間追加計時500周期は別試行として保存し、代表の公開コード500周期・10超過へ混ぜない。

r10はイベント複製の循環参照を除いた。保存フレームの値・状態・失敗記録を旧版と照合したうえで500周期を測り、超過は4回に減った。一時的にCPU上限を上げた別試行も4回超過しており、標準設定には採用しない。両試行の通信返信はすべて20ms以内だが、返信後処理まで含む全工程の合格には至らない。次は記録の保持量を減らす選択式診断を、変換時間も周期内へ含めて検証する。[全条件](hardware-native-cycle-20260928.md)を参照する。

`--power-epoch`は操作者が現在の40V通電区間を識別する宣言。同じ起動のcapture・校正・実機診断への一致と、既存の具体的な電源ラベルへの一致が必要で、Jetson起動IDからモーター電源を推定する処理ではない。準備記録にもその区別を保存する。モデルソースを含むbundleは`--bundle`で明示して設定へ結び付ける。

## 独立したゼロゲイン通信断診断

計画表示は次の1行でできる。

```sh
PYTHONPATH=runtime python3 -B -m singularitydog_hw.watchdog_commissioning \
  --expected-uids inputs/expected-uids.json --group all
```

実行には現在の支持台・脚の離隔・即時40V Off、実機RS05確認、前後ポート、電源世代、確認済み音声、私有保存先を指定する。支持を外す試験ではない。

```sh
PYTHONPATH=runtime python3 -B -m singularitydog_hw.watchdog_commissioning \
  --expected-uids inputs/expected-uids.json --group all \
  --execute-supported-zero-gain --support-in-place --cutoff-ready --rs05-model-confirmed \
  --front-port '<前脚ポート>' --rear-port '<後脚ポート>' \
  --power-epoch '<今回の40V電源世代>' \
  --audio '<確認済み音声.wav>' --audio-sha256 '<音声SHA256>' \
  --audio-device '<確認済みALSAデバイス>' --output '<新規私有ディレクトリ>'
```

実行前に端末で1回Enterを求める。全12軸UID・STOP・生FW・電圧とMITモードを確認し、200ms watchdogを設定・読戻しする。正のKp/Kdは送らない。無効状態へのゼロゲインフレームで再有効化しないことを先に確認し、選択した軸を1台ずつ有効化→ゼロゲイン→両バス210ms無送信→無効状態の返信確認とする。12軸は1回のコマンドで終わり、12回の操作者確認はない。`--group calf/thigh/hip`なら指定4軸だけを対象にする。

最後のゼロゲインのホスト書込み完了から、無効状態返信のホスト受信までを保守的な上限として保存し、250ms以内を要求する。CAN内部の正確な無効化時刻ではない。ゼロ速度・ゼロFFにも量子化の微小バイアスがあり、物理トルクが厳密にゼロとは言わない。

`COMPLETE_COMMAND_LOSS_DIAGNOSTIC`は指令断の限定結果。USBケーブルを実際に抜いた試験や、荷重下の停止・転倒防止は証明しない。USB断確認は未確定として残り、実出力の承認へ自動昇格しない。STOP未確認なら支持を維持して40VをOffにする。

実出力の開始時には、停止実測と結び付けた生FW返信4バイト`version_bytes_hex`を各UIDごとに当日読取りと照合する。通常STOPと版数返信を区別し、文字列の版名からバイト順や番号を推測しない。この処理は起動前だけで、20msループへ追加しない。

## 今日の判定

20msは、最古入力の取得開始→最終ホスト書込みと、返信後の復号・監視処理までの全工程、実際の開始間隔を別表示する。超過周期数を含める。STOP代理24要求と、選択式V3の26要求STOP代理、将来のType1実出力を同じ負荷とみなさない。26要求STOP代理の実測では、計測中の固定クロックが必須の改善要因だったが、全工程と厳密な開始間隔はなお未達である。

静的保持の成功だけで自立と判定しない。支持を外して荷重を受けた記録・映像、滑り/沈み/過負荷/接触なし、全軸停止、再支持を評価する。支持を減らす段階には補助者または全重量を受ける独立した落下受けが必要。詳しい開始・停止・評価は[支持付き実出力](policy-output-validation-20260928.md)と[4段階の試験](ground-trials-20260928.md)を使う。
